# Чек-лист развёртывания на проде

Порт/nginx не входят в этот чек-лист — настраиваются отдельно. Здесь —
всё остальное, что нужно поменять относительно текущей dev-конфигурации
(Docker Desktop, локальный NetBox).

## 1. Скопировать на сервер

- [ ] Скопировать директорию `ip_plan_docker_react/` (код, `Dockerfile`,
      `docker-compose.yml`) — `.env` копировать **не нужно**, он в
      `.gitignore`/`.dockerignore` и не должен путешествовать как есть
      (содержит реальный токен NetBox).
- [ ] На сервере: `cp .env.example .env`, дальше заполнить как ниже.
- [ ] Рядом должен быть доступен чекаут `netbox-sync` (для volumes —
      `config_backups/`, `sync_logs/`, `firewall_blocklists/`, `conf/`).
      Если он лежит не рядом (как на CI-раннере, `DEPLOY_PATH=/opt/scan`) —
      указать реальный путь в `NETBOX_SYNC_DIR` (см. ниже). Подробности —
      `netbox-sync/CLAUDE.md`.

У приложения есть своя БД: хранит сессии, LDAP-зеркалированных пользователей,
реестр блокировок регулятора и настройки раздела «Настройки». По умолчанию
это SQLite (`data/db.sqlite3` — Docker volume `sqlite_data`); с 03.10.2026
вместе с приложением поднимается PostgreSQL 18 (том `pg_data`, см. разделы
9 и 10), и на него приложение переводится переменной `IP_PLAN_DB_ENGINE=postgres`
— только вместе с переносом данных. Миграции применяются автоматически при
каждом старте (`entrypoint.sh` → `manage.py migrate`), вручную запускать не
нужно — но тома `sqlite_data` и `pg_data` **не должны теряться** между
передеплоями, иначе пропадут накопленные письма регулятора и локальные учётки.

- [ ] Секреты PostgreSQL заведены как CI/CD-переменные проекта
      (`POSTGRES_PASSWORD`, `IP_PLAN_DB_PASSWORD`, `NETBOX_SYNC_DB_PASSWORD`,
      `NETOBS_RO_PASSWORD`; `.gitlab-ci.yml` пишет из них `.env.db`). Без
      `.env.db` `docker compose` не стартует вовсе. При ручном развороте —
      `cp .env.db.example .env.db` и заполнить.

## 2. Заполнить `.env`

- [ ] `SECRET_KEY` — сгенерировать новый, не использовать dev-ключ:
      ```
      python3 -c "import secrets; print(secrets.token_urlsafe(50))"
      ```
- [ ] `DEBUG=False`
- [ ] `ALLOWED_HOSTS` — реальный домен/IP, по которому будет открываться
      приложение (например `ip-plan.company.local`).
- [ ] `CSRF_TRUSTED_ORIGINS` — заполнять, если приложение открывается по
      **HTTPS** (нужен полный origin со схемой, например
      `https://ip-plan.company.local`). Без этого Django будет отвечать
      403 на все POST/PATCH/DELETE (сохранение, удаление, кнопки меню),
      даже если `ALLOWED_HOSTS` настроен верно.
- [ ] `USE_X_FORWARDED_PROTO` — выставить `True` **только если**
      nginx-конфиг сам ставит заголовок `X-Forwarded-Proto: https` и не
      пропускает его от клиента напрямую (иначе это даёт возможность
      подделать заголовком "https" и обойти secure-куки). Согласовать
      это с тем, кто настраивает nginx.
- [ ] `NETBOX_TOKEN` — рекомендуется отдельный токен для прод-инстанса,
      а не dev-токен.
- [ ] `NETBOX_VERIFY_SSL` — `true`, если у прод-NetBox валидный
      сертификат (на dev стояло `false` из-за самоподписанного).
- [ ] `NETBOX_DNS_SERVERS` / `NETBOX_DNS_SKIP_PATTERN` — проверить, что
      это те же внутренние DNS-серверы, которые видны именно с сервера,
      где будет жить контейнер (могут отличаться от dev-машины).
- [ ] `NETBOX_SYNC_DIR` — хостовый путь до чекаута `netbox-sync` (см.
      пункт 1). Пусто = сиблинг-директория `../netbox-sync`, подходит
      только если репозитории лежат рядом на диске.
- [ ] `ACL_CONFIG_BACKUPS_DIR` / `SYNC_LOGS_DIR` / `FIREWALL_BLOCKLISTS_DIR`
      — пути ВНУТРИ контейнера до примонтированных данных netbox-sync.
      Трогать только если раскладка внутри контейнера отличается от
      дефолтной точки монтирования в `docker-compose.yml`.
- [ ] `SESSION_COOKIE_NAME` / `CSRF_COOKIE_NAME` — менять только если на
      том же hostname (домен без учёта порта) уже открывается NetBox или
      другой стенд этого приложения с дефолтными именами кук — иначе вход
      в одно тут же разлогинивает другое. Значения по умолчанию уже
      уникальны, специально трогать не обязательно.
- [ ] `LDAP_TLS_CA_CERT` — путь до CA-сертификата для LDAPS, если он не
      системный. Единственный LDAP-параметр, который нельзя поменять из
      интерфейса «Настройки» (см. пункт 7) — только `.env` + перезапуск
      контейнера.

## 3. `NETBOX_URL` — зависит от того, где живёт NetBox

Выбрать один вариант:

- [ ] **NetBox в Docker на этом же сервере** — лучше подключить
      `ip_plan_docker_react` к той же docker-сети и обращаться по имени
      сервиса (например `http://netbox:8080`), без `host.docker.internal`.
- [ ] **NetBox на этом же сервере, но не в Docker** — оставить
      `NETBOX_URL=http://host.docker.internal:8000`. Уже добавлена
      запись `extra_hosts: host.docker.internal:host-gateway` в
      `docker-compose.yml` — на Linux Docker Engine (20.10+) она нужна,
      т.к. в отличие от Docker Desktop это имя там не резолвится само.
- [ ] **NetBox на отдельном сервере** — указать его реальный адрес
      (например `https://netbox.company.local`), `host.docker.internal`
      тут не используется вообще.

## 4. Сетевой доступ для функций сканирования

Пункты меню «Проверить доступность» / «Сканировать порты» / «Резолв DNS»
делают исходящие запросы (ICMP/fping, nmap, DNS) с сервера, где крутится
контейнер — не с дев-машины.

- [ ] Firewall/маршрутизация сервера пускает исходящий трафик до
      внутренних подсетей, которые будут сканироваться.
- [ ] DNS-серверы из `NETBOX_DNS_SERVERS` реально доступны с этого
      сервера (это могут быть другие серверы, чем были доступны с
      dev-машины).

## 6. Первый вход (локальный администратор)

При первом старте `entrypoint.sh` создаёт локальную учётку `admin` с
паролем `admin` (или тем, что задано в `LOCAL_ADMIN_USERNAME`/
`LOCAL_ADMIN_PASSWORD`). Она нужна как аварийный вход: LDAP-подключение
правится из интерфейса, и неудачная правка не должна оставлять снаружи
всех.

- [ ] Войти как `admin` и **сразу сменить пароль** — до смены приложение
      не пускает никуда, кроме страницы смены (это не рекомендация, а
      поведение системы).
- [ ] Убедиться, что вход через FreeIPA тоже работает — учётка `admin`
      его не заменяет, а дополняет.

Повторные перезапуски контейнера пароль не сбрасывают: команда создаёт
учётку только если локальных нет вообще. Если локальный администратор не
нужен совсем — `SEED_LOCAL_ADMIN=false`, но тогда при поломке LDAP
попасть в интерфейс будет нечем.

## 7. Настройки после первого запуска

Параметры подключения к FreeIPA переехали из `ip_plan/ldap_settings.json` в
базу: миграция `0008_seed_ldap_config` при первом `migrate` переносит их
оттуда вместе с паролем из `LDAP_BIND_PASSWORD`, дальше всё правится в
интерфейсе (Настройки → LDAP) и применяется со следующего входа, без
перезапуска.

- [ ] Зайти в Настройки → LDAP, нажать «Проверить подключение» и убедиться,
      что bind проходит. Заодно проверить вход конкретного пользователя —
      эта проверка ловит случай «bind проходит, а логин нет».
- [ ] Проверить, что раздел «Настройки» видят только те, кому положено:
      вкладки «Оборудование»/«Гипервизоры»/«Скан и DNS» требуют `is_staff`,
      вкладки «LDAP» и «Пользователи» — `is_superuser`.

**Важно про `SECRET_KEY`:** им зашифрован bind-пароль в базе. Смена ключа
сделает пароль нечитаемым — вход через каталог перестанет работать, и
пароль нужно будет ввести заново в интерфейсе (для этого и нужен локальный
администратор из пункта 6). Если ключ меняете — сразу после этого зайдите
локальной учёткой и перевведите пароль bind.

## 9. Бэкапы PostgreSQL

Обе базы (`ip_plan` и `netobs`) живут в томе `pg_data`. Копия снимается
`scripts/pg_backup.sh`: `pg_dump -Fc` по каждой базе и
`pg_dumpall --globals-only` (роли) — через `docker compose exec -T` под
пользователем `postgres` по сокету внутри контейнера, поэтому пароль нигде
не передаётся. Файлы с датой пишутся в каталог на хосте **вне тома**
(`BACKUP_DIR`, по умолчанию `/var/backups/ip_plan_pg`, права 0700/0600 —
внутри хеши паролей и шифрованный bind-пароль LDAP), старше 14 дней
(`RETENTION_DAYS`) удаляются. Недописанный дамп не остаётся: файл пишется
во временный и переименовывается только после успеха; при ошибке любого
дампа скрипт выходит с ненулевым кодом.

- [ ] Каталог `BACKUP_DIR` лежит на другом диске/разделе, чем том Docker
      (или копии уезжают дальше по расписанию хоста) — иначе потеря диска
      забирает и базу, и бэкап.
- [ ] В cron хоста (от пользователя, который может `docker compose`)
      добавлена строка — ежедневно в 02:00, до ночного прогона синка в 03:00:

```
0 2 * * * /opt/ip_plan_docker_react/scripts/pg_backup.sh >> /var/log/ip_plan_pg_backup.log 2>&1
```

- [ ] Ручной запуск отработал: в каталоге три файла
      (`ip_plan_*.dump`, `netobs_*.dump`, `globals_*.sql`), код возврата 0.

**Проверка восстановления** — в отдельный временный контейнер, боевой
postgres не трогаем. Сначала роли (иначе `pg_restore` упадёт на `GRANT ... TO
ip_plan_ro`), затем базы:

```
B=/var/backups/ip_plan_pg
docker run --rm -d --name pgrestore_test -e POSTGRES_PASSWORD=x postgres:18
# подождать пару секунд, пока контейнер поднимется (pg_isready)
docker exec -i pgrestore_test psql -U postgres -q < $B/globals_<дата>.sql   # "already exists" для postgres — норма
docker exec pgrestore_test psql -U postgres -c 'create database ip_plan' -c 'create database netobs'
docker exec -i pgrestore_test pg_restore -U postgres -d ip_plan --exit-on-error < $B/ip_plan_<дата>.dump
docker exec -i pgrestore_test pg_restore -U postgres -d netobs  --exit-on-error < $B/netobs_<дата>.dump
```

- [ ] Оба `pg_restore` завершились без ошибок.
- [ ] Число строк в таблицах совпадает с боевой базой (допуск — записи,
      появившиеся после снятия дампа), например для каждой базы:
      `psql -U postgres -d <база> -Atc "select relname, n_live_tup from pg_stat_user_tables order by 1"`
      в боевом (`docker compose exec -T -u postgres postgres psql ...`) и
      во временном контейнере; для `ip_plan` — также `python manage.py db_counts` против восстановленной базы (`IP_PLAN_DB_ENGINE=postgres`, `IP_PLAN_DB_HOST` на временный контейнер).
- [ ] Временный контейнер удалён: `docker rm -f pgrestore_test`.

**Никогда не выполняйте `docker compose down -v` на проде** — флаг `-v`
удаляет тома, в том числе `pg_data` с обеими базами. Останавливать стек
нужно `docker compose down` (без `-v`); последняя копия из `BACKUP_DIR` —
единственная страховка от такой ошибки.

## 10. Выкатка этапа «хранилище наблюдений» (по дням)

Этап меняет два репозитория и выкатывается на прод по дням — смешивать их нельзя:
сбой этапа не должен прятаться за накопленными правками. Мотивы и риски — план
`docs/plans/2026-10-03-0059-feat-observations-store-stage1-plan.md` (KTD9,
«Risk Analysis»). Пуш `netbox-sync` в `main` — это автодеплой на прод; ip_plan
выкатывается вручную. Решение о пуше, ручном деплое и удалении записей из
NetBox принимает пользователь, не исполнитель.

**Каждый день выкатки:** `./bump_version.sh` в выкатываемом репозитории; после
деплоя — проверить номер (в углу ip_plan; `[version=…]` в первой строке лога
синка).

### Критерии go/no-go удаления из NetBox

Удаление (`netobs_import_netbox.py --delete-from-netbox`) необратимо:
восстановления из выгрузки нет, MAC-таблицы в NetBox возвращает только прогон в
старом режиме. Только по явному решению пользователя.

**Go — все условия:**

- [ ] не меньше 7 ночных прогонов подряд без `ERROR netobs` и с успешными
      опросами всех ожидаемых устройств;
- [ ] кабели без необъяснённых расхождений со слепком;
- [ ] поиск проверен на контрольных MAC;
- [ ] бэкап `netobs` восстановлен во временный контейнер (раздел 9);
- [ ] дамп БД NetBox снят непосредственно перед удалением;
- [ ] явное согласие пользователя.

**No-go — любое из:** необъяснённый `CONFLICT`; пропуск правила топологии за
период; записи без пары в `netobs`.

Правила запуска: `--force` на проде не используется; запуск вне окна прогона;
устройство, которое больше не опрашивается (выведено, выключен `sync_macs`),
исключается явным `--exclude-device` по решению пользователя; около 7 тыс.
записей удаления в журнале NetBox — ожидаемый разовый шум. Дамп NetBox как
откат годится только в первые часы после удаления (восстановление откатывает и
все прочие изменения NetBox после дампа); позже — прогон в старом режиме.

### Откат

- **Синк** (пока записи в NetBox не удалены): переименовать `conf/netobs.json`,
  один прогон — кабели совпадают со слепком. Откат синка **не откатывает**
  накопленные с 30.09 коммиты (день 0).
- **ip_plan на SQLite**: CI-переменная `IP_PLAN_DB_ENGINE=sqlite` и повторный
  деплой (остановить `web`, переключить, поднять; правка `.env` на хосте не
  годится — CI перезапишет). **Только до первой записи в PostgreSQL:** перед
  откатом `db_counts --compare` против `counts_target.tsv` из каталога переноса
  и сравнение выгрузки с `dump.json`; при любом отличии — только обратный
  перенос `scripts/sqlite_to_postgres.sh --reverse --stop-web` (иначе теряются,
  в частности, имена объектов xFW и записи регулятора).
- **Импорт**: удалить строки опросов `kind=import` (с их наблюдениями).
- **Смена пароля `netbox_sync`** — в двух местах: `.env.db`/CI-переменная +
  `bootstrap.sh` и `netbox-sync/conf/netobs.json`; иначе синк теряет базу.

### Порядок одного дня (окно — днём, не ночью)

1. `./bump_version.sh` в обоих репозиториях.
2. **Бэкап до миграции netobs 0002** (отката схемы нет, KTD20):

   создадут: `docker compose exec postgres bash /opt/ip_plan_db/bootstrap.sh`.

   `sync_job`/`sync_schedule` выдаёт этот же запуск bootstrap (блок
   совпадает с миграцией). Проверить: `\dp sync_job` в базе `ip_plan`.
