# Чек-лист развёртывания на проде

Порт/nginx не входят в этот чек-лист — настраиваются отдельно. Здесь —
всё остальное, что нужно поменять относительно текущей dev-конфигурации
(Docker Desktop, локальный NetBox).

## 1. Скопировать на сервер

- [ ] Скопировать директорию `ip_plan_docker_react/` (код, `Dockerfile`,
      `docker-compose.yml`) — `.env` копировать **не нужно**, он в
      `.gitignore`/`.dockerignore` и не должен путешествовать как есть
      (содержит реальный токен NetBox).
- [ ] На сервере: `cp .env.example .env`, дальше заполнить как ниже.
- [ ] Рядом должен быть доступен чекаут `netbox-sync` (для volumes —
      `config_backups/`, `sync_logs/`, `firewall_blocklists/`, `conf/`).
      Если он лежит не рядом (как на CI-раннере, `DEPLOY_PATH=/opt/scan`) —
      указать реальный путь в `NETBOX_SYNC_DIR` (см. ниже). Подробности —
      `netbox-sync/CLAUDE.md`.

У приложения есть своя БД (SQLite, `data/db.sqlite3` — Docker volume
`sqlite_data`): хранит сессии, LDAP-зеркалированных пользователей, реестр
блокировок регулятора и настройки раздела «Настройки». Миграции применяются
автоматически при каждом старте (`entrypoint.sh` → `manage.py migrate`),
вручную запускать не нужно — но том `sqlite_data` **не должен теряться**
между передеплоями, иначе пропадут накопленные письма регулятора и локальные
учётки.

## 2. Заполнить `.env`

- [ ] `SECRET_KEY` — сгенерировать новый, не использовать dev-ключ:
      ```
      python3 -c "import secrets; print(secrets.token_urlsafe(50))"
      ```
- [ ] `DEBUG=False`
- [ ] `ALLOWED_HOSTS` — реальный домен/IP, по которому будет открываться
      приложение (например `ip-plan.company.local`).
- [ ] `CSRF_TRUSTED_ORIGINS` — заполнять, если приложение открывается по
      **HTTPS** (нужен полный origin со схемой, например
      `https://ip-plan.company.local`). Без этого Django будет отвечать
      403 на все POST/PATCH/DELETE (сохранение, удаление, кнопки меню),
      даже если `ALLOWED_HOSTS` настроен верно.
- [ ] `USE_X_FORWARDED_PROTO` — выставить `True` **только если**
      nginx-конфиг сам ставит заголовок `X-Forwarded-Proto: https` и не
      пропускает его от клиента напрямую (иначе это даёт возможность
      подделать заголовком "https" и обойти secure-куки). Согласовать
      это с тем, кто настраивает nginx.
- [ ] `NETBOX_TOKEN` — рекомендуется отдельный токен для прод-инстанса,
      а не dev-токен.
- [ ] `NETBOX_VERIFY_SSL` — `true`, если у прод-NetBox валидный
      сертификат (на dev стояло `false` из-за самоподписанного).
- [ ] `NETBOX_DNS_SERVERS` / `NETBOX_DNS_SKIP_PATTERN` — проверить, что
      это те же внутренние DNS-серверы, которые видны именно с сервера,
      где будет жить контейнер (могут отличаться от dev-машины).
- [ ] `NETBOX_SYNC_DIR` — хостовый путь до чекаута `netbox-sync` (см.
      пункт 1). Пусто = сиблинг-директория `../netbox-sync`, подходит
      только если репозитории лежат рядом на диске.
- [ ] `ACL_CONFIG_BACKUPS_DIR` / `SYNC_LOGS_DIR` / `FIREWALL_BLOCKLISTS_DIR`
      — пути ВНУТРИ контейнера до примонтированных данных netbox-sync.
      Трогать только если раскладка внутри контейнера отличается от
      дефолтной точки монтирования в `docker-compose.yml`.
- [ ] `SESSION_COOKIE_NAME` / `CSRF_COOKIE_NAME` — менять только если на
      том же hostname (домен без учёта порта) уже открывается NetBox или
      другой стенд этого приложения с дефолтными именами кук — иначе вход
      в одно тут же разлогинивает другое. Значения по умолчанию уже
      уникальны, специально трогать не обязательно.
- [ ] `LDAP_TLS_CA_CERT` — путь до CA-сертификата для LDAPS, если он не
      системный. Единственный LDAP-параметр, который нельзя поменять из
      интерфейса «Настройки» (см. пункт 7) — только `.env` + перезапуск
      контейнера.

## 3. `NETBOX_URL` — зависит от того, где живёт NetBox

Выбрать один вариант:

- [ ] **NetBox в Docker на этом же сервере** — лучше подключить
      `ip_plan_docker_react` к той же docker-сети и обращаться по имени
      сервиса (например `http://netbox:8080`), без `host.docker.internal`.
- [ ] **NetBox на этом же сервере, но не в Docker** — оставить
      `NETBOX_URL=http://host.docker.internal:8000`. Уже добавлена
      запись `extra_hosts: host.docker.internal:host-gateway` в
      `docker-compose.yml` — на Linux Docker Engine (20.10+) она нужна,
      т.к. в отличие от Docker Desktop это имя там не резолвится само.
- [ ] **NetBox на отдельном сервере** — указать его реальный адрес
      (например `https://netbox.company.local`), `host.docker.internal`
      тут не используется вообще.

## 4. Сетевой доступ для функций сканирования

Пункты меню «Проверить доступность» / «Сканировать порты» / «Резолв DNS»
делают исходящие запросы (ICMP/fping, nmap, DNS) с сервера, где крутится
контейнер — не с дев-машины.

- [ ] Firewall/маршрутизация сервера пускает исходящий трафик до
      внутренних подсетей, которые будут сканироваться.
- [ ] DNS-серверы из `NETBOX_DNS_SERVERS` реально доступны с этого
      сервера (это могут быть другие серверы, чем были доступны с
      dev-машины).

## 5. Собрать и запустить

```
docker compose up -d --build
docker compose logs -f web
```

- [ ] Контейнер стартует без ошибок, `fping`/`nmap` доступны внутри
      (можно проверить: `docker compose exec web which fping nmap`).

## 6. Первый вход (локальный администратор)

При первом старте `entrypoint.sh` создаёт локальную учётку `admin` с
паролем `admin` (или тем, что задано в `LOCAL_ADMIN_USERNAME`/
`LOCAL_ADMIN_PASSWORD`). Она нужна как аварийный вход: LDAP-подключение
правится из интерфейса, и неудачная правка не должна оставлять снаружи
всех.

- [ ] Войти как `admin` и **сразу сменить пароль** — до смены приложение
      не пускает никуда, кроме страницы смены (это не рекомендация, а
      поведение системы).
- [ ] Убедиться, что вход через FreeIPA тоже работает — учётка `admin`
      его не заменяет, а дополняет.

Повторные перезапуски контейнера пароль не сбрасывают: команда создаёт
учётку только если локальных нет вообще. Если локальный администратор не
нужен совсем — `SEED_LOCAL_ADMIN=false`, но тогда при поломке LDAP
попасть в интерфейс будет нечем.

## 7. Настройки после первого запуска

Параметры подключения к FreeIPA переехали из `ip_plan/ldap_settings.json` в
базу: миграция `0008_seed_ldap_config` при первом `migrate` переносит их
оттуда вместе с паролем из `LDAP_BIND_PASSWORD`, дальше всё правится в
интерфейсе (Настройки → LDAP) и применяется со следующего входа, без
перезапуска.

- [ ] Зайти в Настройки → LDAP, нажать «Проверить подключение» и убедиться,
      что bind проходит. Заодно проверить вход конкретного пользователя —
      эта проверка ловит случай «bind проходит, а логин нет».
- [ ] Проверить, что раздел «Настройки» видят только те, кому положено:
      вкладки «Оборудование»/«Гипервизоры»/«Скан и DNS» требуют `is_staff`,
      вкладки «LDAP» и «Пользователи» — `is_superuser`.

**Важно про `SECRET_KEY`:** им зашифрован bind-пароль в базе. Смена ключа
сделает пароль нечитаемым — вход через каталог перестанет работать, и
пароль нужно будет ввести заново в интерфейсе (для этого и нужен локальный
администратор из пункта 6). Если ключ меняете — сразу после этого зайдите
локальной учёткой и перевведите пароль bind.

## 8. Дымовой тест после запуска

- [ ] Таблица IP-адресов открывается и подтягивает реальные данные из
      прод-NetBox.
- [ ] Поиск и фильтры (статус/тэги/подсеть) работают.
- [ ] Inline-редактирование одного поля сохраняется (видно изменение в
      самом NetBox).
- [ ] Добавление и удаление IP работают.
- [ ] Все три пункта кебаб-меню («Проверить доступность», «Сканировать
      порты», «Резолв DNS») отрабатывают без 403/500 в логах.
- [ ] Список писем регулятора открывается, письмо создаётся и
      редактируется, «Создал» проставляется корректно.
- [ ] Раздел «Настройки» открывается, вкладки видны по правам (см. пункт
      7), сохранение любого файла (например `devices.json`) проходит и
      появляется в «Журнале».
