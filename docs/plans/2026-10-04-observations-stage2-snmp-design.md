## Цель

Сбор MAC-таблиц, LLDP и агрегатов по SNMP с периодом от 1 минуты; запуск всех операций, кроме nmap, из ip_plan — по расписанию и вручную; кабели в NetBox, которые поддерживают себя сами там, где доказательство достаточно сильное.

## Решения

| # | Тема | Решение |
|---|---|---|
| 1 | Сборщик | Отдельный контейнер в compose ip_plan. Код netbox-sync монтируется (прод: `/opt/scan`, локально: `${NETBOX_SYNC_DIR:-../netbox-sync}`), в образе только Python и зависимости. При расхождении установленных пакетов с `requirements.txt` — громкий статус |
| 2 | Расписания и задания | Модели Django в базе ip_plan. Сборщик — своя роль (`sync_worker`), права только на эти таблицы. Захват задания — `FOR UPDATE SKIP LOCKED` |
| 3 | Что запускается из ip_plan | Все операции, кроме nmap (он остаётся в cron под root). И по расписанию, и «запустить сейчас» |
| 4 | Интервалы | На каждый вид данных свой, минимум 1 минута. По умолчанию: MAC и ARP ядра — 10 мин; LLDP — 30; агрегаты — 60; топология — после сбора, не чаще раза в 30 мин |
| 5 | Свежесть | MAC текущий, пока его видит хотя бы один из 3 последних **успешных** опросов устройства. Неудачный опрос ничего не меняет. Нет успешного опроса 30 мин — «устарело», без стирания |
| 6 | Хранение наблюдений | Только изменения: наблюдение — интервал «появился — пропал», с VLAN. «Последний раз видели» — из журнала опросов |
| 7 | LLDP и агрегаты | Отдельные таблицы netobs, общий журнал опросов. Тип chassis id и port id храним как есть (subtype) |
| 8 | Реестр платформ | Первая задача. Один файл в netbox-sync: платформа → виды данных → способ (SNMP/SSH) и особенности. ip_plan читает его вместо своих списков |
| 9 | «Ответ распознан» | Сборщик возвращает данные и признак. Распознан и пуст — честный ноль; не распознан — неудачный опрос, текущее не меняется. Исключение из R9 этапа 1 становится не нужным |
| 10 | SNMP и SSH | Один основной способ на вид данных (реестр). SSH — где SNMP не даёт (порт партнёра LACP у Maipu, LACP Huawei, STP и серийники MES24xx, конфиги, ViPNet) и запасной при сбое SNMP. Ночная контрольная сверка SNMP и SSH — отчётом |
| 11 | Порядок платформ | ROS и ISS (MAC) → LLDP на всех → агрегаты ROS/ISS → Maipu → Huawei. Каждый шаг — теневая сверка кабелей |
| 12 | Блокировки | Опрос устройства не ждёт предыдущий, а пропускает такт (`pg_try_advisory_lock`). `lock_timeout` ~10 с, `statement_timeout` ~60 с, `idle_in_transaction_session_timeout` ~60 с |
| 13 | Сбои | Ненулевой код и красный шаг при сбое записи. Недоступная база — одна проверка на прогон, без ожидания на каждом устройстве |
| 14 | Оповещение | Только баннер в ip_plan по `/health` сборщика (состояние не через базу). Внешнее оповещение — вне этапа |
| 15 | Ротация | Подробная история опросов — N дней (7); наблюдения — 90 дней после закрытия интервала. Запускает сборщик раз в час |
| 16 | Аплинки по MAC | Только netobs и пунктир на карте; в NetBox не пишем |
| 17 | Диагностика | Топология пишет решение по каждому порту-кандидату с кодом причины; ip_plan — поиск по устройству и порту, пояснение на карте, список «похоже на аплинк без связи» |
| 18 | Хранение сводки топологии | Сводка прогона, история «без подтверждения», предложения замен, журнал удалений и замен — в netobs. Файлы `topology.json`, `unconfirmed_cables.json` уходят в базу |
| 19 | Действия человека | Через задание: ip_plan проверяет права и создаёт задание, сборщик перепроверяет актуальность и применяет. netobs пишет только netbox-sync |
| 20 | Кто изменил кабель | NetBox меняет токен синка (иначе кабель станет «правленным руками»). Исполнитель — в журнале объекта NetBox: при замене — нового кабеля, при удалении — интерфейсов на обоих концах (проверено на NetBox 4.6.3: журнал кабеля удаляется вместе с ним, журнал интерфейса остаётся) |
| 21 | Права | Удаление кабеля, применение, отклонение, откат — только `netbox-admins` (флаг `is_staff`, проверка `staff_required`) |

## Поддержание кабелей

| Что произошло | Чем доказано | Карта | Режим «предлагать» | Автоматический режим | Кто |
|---|---|---|---|---|---|
| Кабель подтверждён | любой источник | «подтверждён» | — | — | — |
| Новая связь, порты свободны | любой источник | новая линия | кабель создаётся | кабель создаётся | система |
| Нет подтверждения 2 прогона | только молчание | серый | кнопка «удалить» | кнопка «удалить» | `netbox-admins` |
| Устройство не отвечает 30 мин | — | отсчёт на паузе | — | — | — |
| LLDP с обеих сторон — другой сосед | прямое | конфликт + предложение | предложение замены | замена + журнал | `netbox-admins` / система |
| MAC за новым портом ≥ 2 ч, на старом нет | ушёл и пришёл | конфликт + предложение | предложение замены | замена + журнал | `netbox-admins` / система |
| Ситуация вернулась до решения | — | предложение исчезает | «отпало само» | — | система |
| Ручной или правленный кабель | — | «ручной» | никогда | никогда | человек в NetBox |

Исходы предложения: применено / отклонено с причиной / отпало само / применено автоматически / откачено (считается как отклонено).

Переход на автоматику — свой переключатель на вид замены, включает только человек; система лишь сообщает «критерий выполнен»: LLDP — ≥ 2 недель, ≥ 5 предложений, 0 отклонённых; переезд MAC — ≥ 4 недель, ≥ 10 предложений, 0 отклонённых, мало «отпавших».

Предохранители: не больше 3 автоматических замен за прогон (больше — всё уходит в предложения); журнал каждого действия; откат одним действием; ручные и правленые кабели не трогаются.

## Компоненты

### netbox-sync
- `platforms` — реестр платформ; тест-контракт «каждая модель из `devices.example.json` резолвится».
- Сборщики SNMP по видам данных (FDB с VLAN, LLDP, агрегаты, интерфейсы) с признаком «ответ распознан»; особенности платформ — из реестра (имена портов ISS, обход Maipu с `-Cc`, `hwDynFdbPort` Huawei).
- Схема netobs v2: интервалы наблюдений, VLAN, `lldp_neighbors`, `lag_members`, решения топологии, предполагаемые аплинки, сводка прогона, история «без подтверждения», предложения и журнал замен; миграция данных этапа 1.
- Сборщик (`worker`): цикл заданий, пул с ограничением, `pg_try_advisory_lock` на устройство и вид, `/health` (HTTP внутри compose + файл), ротация.
- Топология: чтение из netobs v2, правило свежести, коды причин, предложения и применение замен, записи в журнал объекта NetBox.

### ip_plan
- Модели расписаний и заданий, роль `sync_worker` в `db/bootstrap.sh`.
- Раздел «Задания»: расписание, «запустить сейчас», история, ошибки, состояние сборщика.
- Баннер по `/health` на всех страницах.
- Настройки из таблицы выше.
- Карта: серый «давно не видели», пунктир аплинков, предложения с кнопками для `netbox-admins`, «почему нет кабеля», журнал замен.
- Списки возможностей платформ — из реестра netbox-sync вместо `MAC_CAPABLE_PARSERS` и др.

### compose ip_plan
- Сервис `worker`: образ с зависимостями netbox-sync, монтирование кода, `conf/` (чтение), снимков и `config_backups/` (запись), SSH-ключей (чтение); доступ к `postgres:5432` изнутри compose.

## Порядок работ

1. Реестр платформ поверх нынешних парсеров, без смены поведения; ip_plan читает его.
2. Схема netobs v2 и перенос данных этапа 1; ротация, таймауты.
3. Сборщик, задания и расписания в ip_plan, `/health` и баннер. Первым делом запускает нынешние SSH-шаги — проверка механики без смены источника.
4. Признак «ответ распознан», сигнал о сбое записи.
5. SNMP по платформам с теневой сверкой (п. 11).
6. Диагностика, аплинки на карте, замена и удаление кабелей в режиме «предлагать».
7. Шаги `full_sync.sh` переезжают в задания; в cron остаётся nmap.

## Проверка (локально)

- Каждый шаг SNMP-перехода: ночь в теневом режиме, топология по SSH и по SNMP на одних данных, сравнение кабелей — прежние на месте, новые и пропавшие объяснены.
- Реестр: поведение синка и UI до и после совпадает (тот же набор флагов по моделям, те же кабели).
- netobs v2: после миграции «текущее» совпадает с этапом 1 на тех же данных.
- Сборщик: ручное и плановое задание, параллельные задания одного устройства (пропуск такта), недоступная база (баннер, без ожидания на устройствах), перезапуск контейнера посреди задания.
- Замены: предложения на подстроенных данных (переезд MAC, смена LLDP-соседа), применение, отклонение, откат, предел 3 за прогон, запись в журнал объекта NetBox.
