# Серверный шлюз удалённого доступа из ip_plan (исследование, 01.10.2026)

Вопрос: вместо локальных клиентов (ssh://, vnc://, .rdp, .vv — см. CLAUDE.md
«Подключение к хосту») поднять ещё один контейнер и подключаться к хостам
через него, чтобы сессия открывалась в модальном окне или соседней вкладке.
Статус: только исследование, ничего не внедрено.

> **Обновление 02.10.2026.** Решено и сделано на локальном стенде: готовый
> Guacamole 1.6.0 + auth-json, сессия в **новой вкладке** (не iframe —
> поэтому реверс-прокси локально не нужен, Guacamole на соседнем порту 8091),
> протоколы SSH / RDP / VNC и консоль ВМ RedVirt по VNC. Мотив — «всё в
> браузере» и разнородные российские ОС на рабочих станциях. Что выяснилось
> по ходу и расходится с текстом ниже:
> - доступ сервера к хостам на MDC уже открыт: правило `NETBOX_SCAN` xFW
>   (Local №1, Forward №13, набор 1776) пропускает с `10.1.108.69` всё;
>   туннели к RDC/офису и уместность использования «сканирующего» правила
>   не проверены и не согласованы;
> - у всех 28 запущенных ВМ RedVirt на MDC есть консоль VNC — SPICE в
>   браузере не нужен; офисный `vmm.office` не проверен (недоступен);
> - Guacamole в покое занимает ~170–190 МБ, guacd ~25 МБ; образы — 1,15 ГБ и
>   390 МБ на диске;
> - на проде nginx уже есть, остаётся `location /guac/` и переменные в CI.
>
> Как устроено — `CLAUDE.md`, раздел «В браузере — шлюз Apache Guacamole».

## Кандидаты

| Вариант | Протоколы | Что это | Оценка |
|---|---|---|---|
| **Apache Guacamole** (guacd + веб-клиент на Java + расширение `guacamole-auth-json`) | SSH, Telnet, VNC, RDP, Kubernetes | Зрелый HTML5-шлюз, официальные docker-образы, запись сессий, запрос логина/пароля у пользователя прямо в браузере, если их не передали | Основной кандидат |
| **guacamole-lite** (Node.js вместо Java-клиента, свой фронт на `guacamole-common-js`) | те же, через guacd | Меньше и легче, без БД, токен AES-256 с параметрами соединения; фронт — полностью наш (можно встроить в drawer) | Запасной, если Java-контейнер неприемлем; больше нашего кода |
| Набор узких инструментов: ttyd/wetty/sshwifty (SSH), noVNC+websockify (VNC), Myrtille (RDP) | по одному | Три разных стека, три разных UI | Не рекомендуется |
| **spice-html5** + websockify | SPICE | Оригинальный проект архивирован в декабре 2023; есть форки (spice-web-client-modernized); без TLS-каналов, без USB/аудио | Хрупко; только при острой нужде |
| Guacamole native SPICE (`libguac-client-spice`, PR apache/guacamole-server#688) | SPICE | Полноценный модуль, но PR ещё **открыт** (август 2026), в релизах 1.6.x его нет | Ждать |
| VMware HTML Console SDK (WebMKS 2.2.1) | консоль ВМ vSphere | Браузер сам соединяется с ESXi-хостом по wss с одноразовым webmks-билетом; нужен прямой доступ браузера к хостам 443 | Отдельная история, не шлюз |

## Как встроить Guacamole в ip_plan (эскиз)

1. `docker-compose.yml` ip_plan: два сервиса — `guacd` (`guacamole/guacd`) и
   `guacamole` (`guacamole/guacamole`, `JSON_ENABLED=true`,
   `JSON_SECRET_KEY=<128 бит>`), без MySQL/Postgres: пользователей и
   соединений в Guacamole не заводим вовсе.
2. Один хост и origin для ip_plan и Guacamole — нужен реверс-прокси (сейчас
   `web` торчит напрямую на 8090, nginx в compose нет). Иначе iframe на другом
   origin упрётся в SameSite-cookie и X-Frame-Options.
3. Клик «SSH» в меню строки → `POST /ip/<id>/connect/?proto=ssh` в ip_plan →
   сервер собирает JSON `{username: <логин ip_plan>, expires: now+90s,
   connections: {"ssh 10.0.0.1": {protocol: "ssh", parameters: {hostname,
   port}}}}`, шифрует (AES-128-CBC + HMAC-SHA256, формат auth-json),
   обменивает на токен через `/guac/api/tokens` и отдаёт браузеру URL
   `/guac/#/client/<id>?token=…`.
4. Браузер открывает URL в iframe модалки/drawer или в новой вкладке —
   настройка пользователя (SSH удобнее в окне, RDP/VNC — во вкладке на весь
   экран). Guacamole сам спрашивает логин/пароль (SSH, RDP NLA) — **пароли в
   ip_plan не хранятся** и не проходят через наш бэкенд.
5. Журнал: ip_plan пишет «кто, когда, к какому хосту, каким протоколом»;
   при необходимости включается запись сессий Guacamole (`recording-path`).

## Что это даёт и чего стоит

Плюсы: ничего не ставить на рабочие станции; одинаково на macOS/Windows/Linux;
единая точка аудита; можно ограничить доступ ролями ip_plan (LDAP уже есть).

Минусы и риски:

- **Сеть и политика.** Шлюзу нужен L3-доступ ко всем хостам на 22/5900/3389.
  Сейчас это разрешено только админским станциям, политику xFW придётся
  расширить на сервер ip_plan — появляется одна точка с доступом ко всему
  управлению. Компенсации: LDAP-вход, короткоживущие токены, запись сессий.
- **Трафик через сервер**: RDP/VNC-картинка кодируется в guacd, нагрузка на
  CPU сервера; для нескольких админов это некритично.
- **Java-контейнер** Guacamole — порядка 300–500 МБ памяти; guacd лёгкий.
- **SPICE в браузере сейчас нет** (см. таблицу). Для ВМ RedVirt практичнее:
  у машины включить графику SPICE+VNC и открывать **VNC через Guacamole**
  (`POST …/graphicsconsoles/<vnc>/ticket` даёт пароль на 120 с, хост и порт —
  из консоли), а SPICE оставить файлом .vv для remote-viewer. Для vCenter —
  VMRC-ссылка или WebMKS (нужен доступ браузера к ESXi:443).
- **Прод** ip_plan деплоится вручную; появятся 2 новых сервиса и прокси.

## Трудоёмкость (оценка)

- MVP (прокси + guacd + guacamole + auth-json + пункт меню «во вкладке»): 2–3 дня.
- Модалка/drawer с iframe, пауза горячих клавиш таблицы, журнал: +1 день.
- Консоль ВМ RedVirt по VNC через Guacamole (ticket API): +1–2 дня.
- SPICE в браузере: не планировать, ждать релиза Guacamole с libguac-client-spice.

## Предложение

Фаза 2 — Guacamole с auth-json как дополнение к уже сделанным локальным
клиентам (их оставить как запасной путь и как единственный для SPICE).
Перед стартом согласовать: разрешение на доступ сервера ip_plan к хостам в
политике xFW, реверс-прокси в compose, приемлемость Java-контейнера, NLA на
Windows-хостах.
