# Разбор документов регулятора (IOC-парсер) — дизайн

Дата: 2026-09-07. Статус: **реализовано**.

## Задача

Письма/бюллетени регулятора (в духе рассылок ФСТЭК) содержат индикаторы
компрометации (IOC) в **депрофанированном** виде (`85[.]190[.]99[.]6`,
`hxxps[:]//...`) — вручную переносить их в реестр блокировок медленно и
чревато опечатками. Нужен парсер PDF/DOCX, извлекающий IP/домены/URL/SHA256,
плюс встраивание в страницу письма: загрузка файлов/папки → редактируемое
превью → ручное подтверждение → сохранение в `RegulatorEntry`.

## Модель

`RegulatorEntry.KIND_CHOICES` получил четвёртый вариант — `("hash", "IOC")`.
Не `"sha256"`: это единственное, что сейчас сюда попадает, но само поле
названо шире («не сетевой IOC» — файловый), чтобы MD5/SHA1, если понадобятся
позже, легли в тот же бакет без миграции существующих записей. Форма
(`RegulatorEntryForm`) валидирует `kind="hash"` как 64-символьный hex.

## Парсер (`ip_plan/services/ioc_parser.py`)

Framework-agnostic модуль (без импорта Django) — пригоден и для
management-команды (`ioc_scan`), и для вызова из view напрямую на файлах из
`request.FILES`, без сохранения на диск.

### Извлечение текста

- PDF — `pdfplumber`, `page.extract_text()` постранично, строки склеены в
  один список по всем страницам подряд.
- DOCX — `python-docx`: `document.paragraphs`, затем
  `table.rows[].cells[].paragraphs` для каждой таблицы (в этом порядке).
- Ошибка чтения (защищённый паролем/битый PDF, повреждённый DOCX, PDF без
  извлекаемого текста) — файл пропускается с `warning`, не бросает
  исключение наружу.
- Неподдерживаемое расширение — тоже `warning`, не ошибка.

### Склейка строк, разорванных переносом посреди URL

Ключевая сложность: PDF-экстрактор переносит строки визуально, как в
оригинале. Обычные построчные списки (`IP;` на каждой строке, или вообще без
`;`) переносить НЕЛЬЗЯ — а длинный `hxxp`-URL иногда рвётся посреди токена
без пробела и без завершающей пунктуации.

Правило (`join_broken_url_lines`): применяется **только** к строкам,
содержащим `hxxp`. Если такая строка не заканчивается одним из `; . , )` и
следующая строка начинается с ASCII-буквы/цифры — первое «слово» следующей
строки приклеивается без пробела, остаток обрабатывается как отдельная
строка дальше. Проверка повторяется (URL может переноситься больше одного
раза подряд). Строки без `hxxp` эта логика не трогает вообще — построчные
списки IOC в приложениях к письмам (без `;` на конце) остаются нетронутыми.

### Порядок применения регулярок (чтобы не задвоить совпадения)

1. **SHA256** — на исходном (не депрофанированном) тексте, независимо от
   остального пайплайна (не пересекается по паттерну с остальными).
2. **URL** — раньше IP/доменов; IP/домен внутри найденного URL не должен
   всплыть отдельным индикатором. Найденные URL заменяются на пробел перед
   следующими шагами.
3. **IP с «приклеенной сноской»** (`IP_FOOTNOTE_RE`, отдельный проход) —
   строгий `IP_RE` в принципе НЕ матчит `89[.]221[.]203[.]162l` (после
   последнего `\d{1,3}` требуется `\b`, а между цифрой и буквой границы
   слова нет — regex просто не находит совпадение). Отдельный паттерн с
   `[A-Za-z]{1,2}` на конце ловит именно такие случаи; хвостовые буквы
   отсекаются, результат помечается `needs_review`.
4. **Обычные чистые IP** — из остатка, после IP-с-сноской.
5. **Домены** — из остатка после IP; совпадения, которые сами являются
   «числа через `[.]`», отфильтровываются (это IP, не домен — защита от
   ложных срабатываний `DOMAIN_RE` на числовых последовательностях, не
   распознанных как IP из-за нестандартного числа октетов).

### Валидация и «грязные» случаи

- IP: каждый октет должен быть `0–255` — иначе индикатор всё равно
  сохраняется (не отбрасывается молча), но с `needs_review=true`.
- Footnote-артефакт (`162l;`): после отсечения 1-2 хвостовых латинских букв
  и повторной проверки диапазона — `needs_review=true`, `note` объясняет
  причину.
- Домены — TLD не ограничен списком (включая `.onion`).
- Рефанжинг (`refang()`) — **только текстовая замена** (`[.]`→`.`,
  `[:]`→`:`, `hxxp`→`http`) в строковом поле результата. Никакого
  превращения в кликабельную ссылку, никаких сетевых запросов — письма
  регулятора прямо запрещают переход по этим адресам, парсер не должен
  даже теоретически давать для этого возможность.

### Агрегация

Дедупликация — глобально по всей папке/по всем загруженным в рамках одного
разбора файлам (`Indicator.source_files`/`occurrences`), не глобально по
всей истории реестра — повторный разбор тех же файлов или другого письма
не проверяется на дубликаты с уже существующими `RegulatorEntry` (та же
модель поведения, что и у ручного ввода/CSV-загрузки в этом приложении —
нигде в реестре нет глобальной уникальности по значению).

## CLI (`python manage.py ioc_scan <folder>`)

Django management-команда (не отдельный argparse-скрипт) — `add_arguments`
даёт `--recursive`, `--per-file`, `--out`; работает в том же контейнере/venv,
где уже стоят `pdfplumber`/`python-docx`, без отдельной установки
зависимостей для standalone-запуска. Не трогает NetBox/БД — чистое чтение
файлов и печать JSON (см. формат в исходном ТЗ).

## Веб-интеграция (детальная страница письма)

Новый блок «Разбор документов» под строкой приёма (`regulator_document_detail.html`):
- **Файлы** — обычный `<input type=file multiple>`.
- **Папка** — `<input type=file webkitdirectory multiple>`.

Оба поля называются `ioc_files` — с точки зрения Django (`request.FILES.getlist`)
выбор папки и выбор нескольких файлов неотличимы, один и тот же view
(`regulator_document_ioc_parse`) обслуживает оба варианта.

Файлы **не сохраняются на диск** — `parse_file()` читает каждый прямо из
Django `UploadedFile` (файлоподобный объект, pdfplumber/python-docx
принимают такие напрямую) и тут же забывает. Результат — HTML-превью
(`_regulator_ioc_preview.html`): редактируемая таблица (тип — select,
значение — text input, автоматически подставленный тип на основе того, что
нашёл парсер), с «Как в тексте / где встречалось» (депрофанированная форма +
файлы-источники) и бейджем «проверить» на `needs_review`. Кнопка «Убрать» —
чисто клиентская (JS, удаляет `<tr>`), ничего не отправляет на сервер.

«Сохранить в письмо» отправляет параллельные массивы `ioc_kind[]`/`ioc_value[]`
(порядок гарантирован DOM-порядком полей формы, `getlist()` возвращает оба
списка в одном порядке независимо от того, сколько строк удалено кнопкой
«Убрать» до отправки). Валидация — той же `RegulatorEntryForm`, что и у
ручного ввода. Как и CSV-загрузка — хотя бы одна невалидная строка (уже
после правок оператором) отклоняет **весь** список целиком, ничего не
сохраняется, ошибки построчные, отредактированные значения остаются в
форме для повторной попытки.

## Проверено вживую

- Синтетические Python-строки на все ловушки из ТЗ (перенос URL через `/`,
  перенос посреди токена с `[:]`, IP внутри URL не задваивается, footnote-
  артефакт с пометкой `needs_review`, построчный список без `;` не
  склеивается, невалидный октет помечается, обычная (не депрофанированная)
  http-ссылка не попадает в результат) — все прошли.
- Реальный DOCX (paragraphs + таблица) и реальный PDF (сгенерированный
  программно, с намеренным переносом URL между строк и обычной ссылкой
  вперемешку с депрофанированными индикаторами) — через `ioc_scan` и через
  веб-форму: извлечение, дедупликация между файлами (SHA256 встретился в
  обоих, `occurrences=2`), полный цикл разбор → правка (убрал строку,
  испортил и исправил значение) → сохранение → записи появились в реестре
  письма с правильными типами и статусом «активна».

## Не сделано / вне рамок этой задачи

- Сверка точных количеств из чек-листа ТЗ (таблица «url/ip/domain/sha256»
  по конкретным файлам пользователя, включая примеры-ловушки вроде
  `hxxps[:]//api[.]telegram[.]org/bot...`, IP-с-сноской `89[.]221[.]203[.]162`
  в файле 7 и т.д.) — не выполнена: у исполнителя нет доступа к реальной
  папке с исходными письмами пользователя. Логика проверена на
  синтетических копиях всех перечисленных в ТЗ примеров-ловушек дословно
  (см. раздел "Проверено вживую"), но финальная сверка с реальными файлами
  остаётся за пользователем — команда `python manage.py ioc_scan <папка>`
  готова для этого прогона.
