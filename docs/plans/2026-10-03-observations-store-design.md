# Хранилище наблюдений вне NetBox и перевод ip_plan на PostgreSQL — этап 1

Дата: 03.10.2026. Затрагивает два репозитория: `ip_plan_docker_react` и `netbox-sync`.
Связанные материалы:
- `NETBOX/topology-review-2026-10-02.md` — ревью построения связей;
- `NETBOX/snmp-features-2026-10-02.md` — что отдаёт SNMP;
- `netbox-sync/CLAUDE.md`, раздел «MIB».

## Зачем

- **Журнал изменений NetBox забит записями MAC-таблиц.** В NetBox сейчас 96 418 записей журнала, из них 79 789 (83%) — создание и удаление записей `mac-table` в `dcim/mac-addresses`. Один полный прогон даёт около 24 тысяч таких записей. При опросе раз в 10 минут (этап 2) было бы около 1,7 млн в сутки.
- **Читает эти записи только `netbox_lldp_topology.py`.** ip_plan их не читает.
- **Записи хранятся без времени наблюдения.** Из-за этого нельзя отличить свежие данные от устаревших. Ревью нашло кабель, держащийся на записи трёхмесячной давности.

## Решения

| # | Решение |
|---|---|
| 1 | NetBox хранит оборудование, кабели, серверы и ВМ. MAC-таблицы и ARP в NetBox больше не пишутся |
| 2 | Наблюдения хранятся в PostgreSQL, в отдельной базе `netobs`. Её схемой владеет netbox-sync |
| 3 | ip_plan переходит с SQLite на PostgreSQL, база `ip_plan`. Схемой владеет Django |
| 4 | Обе базы живут в одном контейнере `postgres:18` в compose ip_plan, на хосте `netbox.sicmt.local` (там же синк и боевой NetBox, установленный без Docker). PostgreSQL слушает только `127.0.0.1` |
| 5 | Счётчики (нагрузка, ошибки, температура) — из Zabbix, не собираем |
| 6 | Нынешние записи `mac-table`/`arp-table` переносятся в `netobs`; из NetBox удаляются после сверки кабелей |
| 7 | **Логика сбора не меняется** (SSH и парсеры те же). Меняется только место хранения. SNMP — этап 2, после отчёта |
| 8 | Миграции `netobs` — первый шаг `full_sync.sh` |
| 9 | Поиск по MAC/IP в ip_plan входит в этап 1 |

## Архитектура

```
хост netbox.sicmt.local
├── netbox-sync (/opt/scan, cron)
│   ├── netobs.py                — подключение, запись, чтение, миграции
│   ├── netobs/migrations/*.sql  — схема netobs
│   ├── netbox_devices_sync.py   — MAC-таблицы и ARP пишет в netobs
│   ├── netbox_lldp_topology.py  — таблицы адресов читает из netobs; ARP ядра пишет в netobs
│   └── netobs_import_netbox.py  — разовый перенос из NetBox
└── docker compose ip_plan
    ├── postgres:18 (127.0.0.1:5432, том pg_data)
    │   ├── ip_plan  — роль ip_plan (владелец)
    │   └── netobs   — роль netbox_sync (запись), роль ip_plan_ro (чтение)
    └── ip_plan (Django): default → ip_plan; netobs → netobs (только чтение)
```

Локально — тот же compose. Прод и локальное окружение остаются полностью раздельными.

## Модель данных `netobs`

**`schema_version`** — применённые миграции.

**`poll_runs`** — по одной строке на снятый вывод:
`id, device, source, complete, started_at, finished_at, ok, rows, error`.

**`observations`**:
`id, nb_device, sync_key, interface, vlan, mac macaddr, ip inet, source, first_seen, last_seen, seen_count, last_run_id`.

- `source`:
  - `mac-table` — FDB коммутатора;
  - `arp-table` — ARP ViPNet и Континента/Jinn/TLS;
  - `arp-l3` — ARP ядра из шага топологии, нужен для поиска по IP.
- `nb_device` — имя устройства в NetBox (ноды ViPNet называются собой); `sync_key` — ключ `devices.json`.
- Уникальность: `(nb_device, interface, coalesce(vlan, 0), mac, source)`. Повтор обновляет `last_seen`, `seen_count`, `last_run_id`.
- `vlan` в этапе 1 пуст: нынешние парсеры его не сохраняют.
- Индексы: `mac`, `ip`, `(nb_device, interface, source, last_seen)`.

### Текущее содержимое порта — сознательно по-старому

Сейчас на порту лежит последний снимок этого порта, а порт, пропавший из вывода, хранит старые записи бессрочно. В этапе 1 это поведение **сохраняется**, чтобы сверка кабелей до и после была осмысленной:

- обычный источник: текущее = строки с наибольшим `last_seen` для `(nb_device, interface, source)`;
- источник с `complete = true` (Континент по SNMP): текущее = строки последнего успешного опроса устройства целиком (пропавший порт очищается, как сейчас);
- устройства с эффективно выключенным `sync_macs` отсеиваются по `sync_key`, как сейчас.

Исправление (правило свежести, окно наблюдения) — этап 2.

## Компоненты

### netbox-sync

**`netobs.py`.** Без побочных эффектов при импорте. Реквизиты — в `conf/netobs.json`: новый секретный файл, поэтому он сразу добавляется в `.gitignore` и в исключения rsync в `.gitlab-ci.yml`.

| Функция | Что делает |
|---|---|
| `migrate()` | применяет `netobs/migrations/*.sql` по порядку; повторный запуск ничего не меняет |
| `start_run` / `store` / `finish_run` | один вывод — одна транзакция |
| `current_observations()` | текущее содержимое портов по правилам выше |

**`netbox_devices_sync._store_mac_table`** пишет в `netobs` вместо `dcim/mac-addresses`. Через неё же идут ARP ViPNet и Континента.

**`netbox_lldp_topology`:**
- `NetBoxIndex.observed` строится из `current_observations()`;
- `collect_device` дописывает ARP ядра как `arp-l3`;
- снимок `latest.json` и логика правил не меняются.

**`full_sync.sh`:** первый шаг — `python3 -c "import netobs; netobs.migrate()"` (или отдельный скрипт), остальные шаги без изменений.

**`netobs_import_netbox.py`:**
- по умолчанию читает NetBox и пишет в `netobs` (`last_seen = created`, `first_seen = NULL`, `seen_count = 1`, в `poll_runs` — отметка «перенос из NetBox»);
- удаляет из NetBox только с флагом `--delete-from-netbox` и только записи, уже найденные в `netobs`.

Новая зависимость: `psycopg[binary]`.

### ip_plan

- `DATABASES["default"]` → `ip_plan`, `DATABASES["netobs"]` → `netobs` под ролью только для чтения; реквизиты — в `.env` compose.
- Маршрутизатор баз: миграции и запись в `netobs` запрещены.
- Перенос данных: `dumpdata` из SQLite → `migrate` на PostgreSQL → `loaddata`. Сейчас это 0,6 МБ, 8 моделей плюс пользователи и сессии; специфичного для SQLite кода нет.
- **Страница «Поиск MAC/IP».** Вход — MAC целиком или частью либо IP. Результат: устройство, порт, источник, первое и последнее появление, история (все порты, где MAC встречался). Отметка «аплинк/транзит», если за портом больше одного адреса. Поиск по IP идёт через ARP (`arp-table`, `arp-l3`) к MAC, а дальше как поиск по MAC. Запросы — SQL через подключение `netobs`, без моделей Django.

## Обработка ошибок

Принцип проекта: отсутствие данных — не доказательство отсутствия связи.

| Ситуация | Поведение |
|---|---|
| PostgreSQL недоступен на шаге миграции | шаг падает с внятной ошибкой, остальные шаги `full_sync.sh` идут |
| недоступен при записи MAC | `ERROR netobs` по устройству; обходного пути через NetBox нет; интерфейсы, IP, агрегаты синхронизируются как обычно |
| недоступен при чтении в топологии | правило «таблица адресов» пропускается с `WARN`; кабели источников `MAC-таблица`, `ARP`, `MAC-таблица + ARP` исключаются из отчёта «без подтверждения» этого прогона |
| сбой посреди записи вывода | транзакция откатывается: нет ни строк, ни `ok` |
| `netobs` недоступна в ip_plan | страница поиска пишет «хранилище наблюдений недоступно», остальное работает |
| повторный импорт из NetBox | без дублей (уникальный ключ) |

## Тестирование

**Автотесты** (без сети, PostgreSQL — тестовая база в том же контейнере):
- `netbox-sync/tests/test_netobs.py`:
  - повтор обновляет, а не дублирует;
  - текущее содержимое порта по старым правилам, **включая пропавший порт со старыми записями**;
  - `complete = true` очищает пропавший порт;
  - откат транзакции;
  - отсев по `sync_macs`;
  - идемпотентность миграций;
  - импорт фикстуры из NetBox без дублей.
- Существующие тесты топологии остаются зелёными на данных из `netobs`.
- ip_plan: поиск по полному MAC, по части, по IP; маршрутизатор не даёт писать в `netobs`; недоступная `netobs` не роняет страницу.

**Прогоны (локально):**
1. Слепок «до»: кабели NetBox и `topology.json`.
2. Перенос ip_plan на PostgreSQL; проверка входа (LDAP и локальная учётка), реестра, настроек, карты.
3. Импорт `mac-table`/`arp-table` в `netobs`.
4. Топология по снимкам на копии `lldp_snapshots` → **кабели совпадают со слепком 1:1**.
5. Полный прогон → повторная сверка; записей `dcim.macaddress` в журнале изменений NetBox за прогон — 0.
6. Удаление старых записей из NetBox → прогон → сверка.

**Прод** — тот же порядок после отчёта по локальному окружению, с резервной копией SQLite ip_plan и NetBox перед переносом.

## Критерии готовности этапа

- Кабели после перехода совпадают с прежними; каждое расхождение объяснено.
- ip_plan работает на PostgreSQL со всеми прежними данными.
- Записи `mac-table` не попадают в журнал изменений NetBox.
- Поиск по MAC/IP находит адрес там же, где его показывала MAC-таблица в NetBox.
- Отчёт по этапу: `docs/plans/<дата>-observations-store-report.md` — сделанное, сверка кабелей, объём журнала до и после, время шагов, проблемы, задел для этапа 2.

## Вне этапа 1
