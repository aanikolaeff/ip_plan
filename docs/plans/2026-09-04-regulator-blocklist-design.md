# Блокировки регулятора — дизайн

Дата: 2026-09-04. Статус: **фаза 1 реализована** (плюс UX-итерация — см. ниже),
фаза 2 (сверка с firewall) — netbox-sync готов, страница сверки не начата.

## UX-итерация: детальная страница письма (после первого прохода фазы 1)

Изначальный workflow (модалка "+ Запись" с выбором письма из выпадающего
списка на КАЖДУЮ запись) оказался неудобным — письмо приходится искать
заново для каждой следующей записи. Пересобрано под другой principle:
"добавил письмо → работаешь внутри него".

- `/regulator/document/<id>/` — новая страница письма. Строка приёма
  ("ПРИЁМ": сегментированный `IP/FQDN/URL` на голых radio + поле значения +
  "Добавить") прямо под заголовком, всегда видна. Успех дописывает `<tr>` в
  конец таблицы (`hx-swap=beforeend`) без перезагрузки, поле очищается и
  получает фокус — ввод записи за записью, не отрываясь от клавиатуры.
  Выбранный тип НЕ сбрасывается между записями (типична ситуация — десяток
  FQDN подряд из одного письма).
- Ошибка валидации не трогает таблицу вообще — только OOB-обновление
  `#quick-add-error` рядом со строкой приёма, введённое значение остаётся в
  поле (не наказываем повторным вводом при опечатке).
- "+ Письмо" → успех → `HX-Redirect` сразу на страницу нового письма
  (никакого промежуточного возврата к общему списку).
- `/regulator/` (общий список) — упрощён: только обзор писем (клик →
  открывает деталку) + отдельный блок "Поиск по всем записям" (сквозной,
  не привязан к письму — для "встречается ли IP X где-то у нас"). Общая
  кнопка "+ Запись" без письма убрана — источник исходного неудобства.
- Действия Снять/Восстановить/Удалить остались общими (`regulator_entry_revoke`
  и т.д.) для обоих контекстов — `return_document_id` (скрытое поле формы
  или `hx-vals`) говорит `_regulator_saved_response()`, что OOB-обновлять:
  `#document-entries-body` (только таблица письма) или `#regulator-page-body`
  (весь общий список, как раньше).

## Задача

Регулятор присылает сырые PDF со списками блокировок (IP/FQDN/URL).
Сейчас обрабатываются вручную. Нужно: хранить структурированно, отдельная
кнопка в шапке рядом с ACL.

## Решения (обсуждены с пользователем)

1. **Извлечение из PDF** — только ручной ввод в форму, без парсинга PDF
   (compliance-чувствительная задача, риск авто-распознавания не оправдан).
2. **Хранение** — первые настоящие Django-модели в проекте (не memory-parse,
   как ACL Lookup): письма регулятора накапливаются во времени, нужна
   история/статусы, а не зеркало текущего файла на диске.
3. **Группировка** — и по письмам (номер/дата), и общий плоский список.
4. **Статус записи** — `active`/`revoked`, не физическое удаление: регулятор
   иногда снимает блокировки, история нужна для аудита. Физическое удаление
   оставлено отдельным действием — только для исправления ошибки ввода.
5. **URL vs domain** — firewall фильтрует только по DNS/IP, не по path;
   `RegulatorEntry.match_value` для `kind=url` — только домен из URL (на
   будущее, если появится URL-фильтрация). Сам `value` хранит URL целиком.

## Фаза 1 (реализовано)

### Модель данных (`ip_plan/models.py`)

```
RegulatorDocument: reference_no, document_date, note
RegulatorEntry: document (FK, PROTECT), kind (ip/fqdn/url), value,
                match_value (вычисляется в save()), status (active/revoked),
                revoked_at, revoked_reason
```

### UI

- Вкладка «Блокировки» в постоянной шапке, рядом с ACL (`base.html`).
- `/regulator/` — один URL на обычный GET и HTMX (тот же принцип, что у
  `acl_lookup`: `hx-push-url`, `HX-Request` header переключает полный
  шаблон/партиал) — поиск (`q`) + фильтры (`kind`/`status`/`document`).
- Секция «Письма» (обзор: номер/дата/примечание/кол-во записей/активных,
  клик по номеру фильтрует записи ниже) + секция «Записи» (плоский список,
  тип/значение/письмо/статус/действия).
- Модалки (общий `#modal-content`, как везде в проекте): «+ Письмо»,
  «+ Запись» (с опциональным prefill письма — кнопка у конкретного письма
  в обзоре), «Снять» (причина, необязательна). «Восстановить»/«Удалить» —
  прямые POST-кнопки (`hx-post`, `hx-swap="none"` + OOB-обновление списка).
- После любого действия — `_regulator_saved_response()` (аналог
  `_saved_response` у IP-таблицы): OOB `outerHTML` всего `#regulator-page-body`
  + `HX-Trigger: close-modal, show-toast`. Фильтры сбрасываются к дефолтным
  после действия — простая цена за то, что модалка не обязана знать текущие
  фильтры фоновой страницы.

### Побочная находка и фикс

`.table`-строки (Bootstrap) оставались белыми в тёмной теме — `--bs-table-bg`/
`--bs-table-color` нигде не переопределялись. Не было видно раньше: ACL —
единственная страница с этим классом — всё это время пустовала (отдельный
баг парсинга). Починено в `style.css` (`:root[data-theme="dark"] .table {...}`).

## Фаза 2 (спроектирована, не реализована)

Сверка регуляторного списка с реально применёнными правилами на firewall
(xFW 5000 ViPNet, устройство `xfw5000-mdc`, `netbox-sync/devices.json`).

Подключился напрямую и нашёл рабочие команды (SSH, `paramiko`, тот же
`legacy_crypto`, что уже используют остальные шаги `netbox-sync`):

- `firewall object show` → секция **Ip Objects** — нумерованные объекты
  (`Num Name Creation-type`, затем значения через запятую до `---`).
  Найдены реальные объекты блокировки: `BLOCK_BY_IP_2` (сырые IP) и
  `BBDNS_1` (FQDN).
- `firewall rules show` → секция **Forward Rules** подтверждает, что эти
  объекты реально применены: правила `BLOCK_OUTSIDE_IN_BY_LIST`
  (`drop @any @BLOCK_BY_IP_2 -> @any`) и `BLOCK_INSIDE_OUT_BY_LIST`
  (`drop @any @any -> @BBDNS_1, @BLOCK_BY_IP_2`).

Примерный план (не начат):

1. `netbox-sync`: новый скрипт (или шаг `full_sync.sh`) — SSH на xFW,
   `firewall object show`, парсер под секцию Ip Objects, сохранение
   снимка (например `firewall_blocklists/<device>/latest.json`,
   `{"BLOCK_BY_IP_2": [...], "BBDNS_1": [...]}`) — список объектов-целей
   вынести в конфиг устройства (не хардкодить имена).
2. `ip_plan_docker_react`: bind-mount этого снимка (тот же приём, что
   `NETBOX_SYNC_DIR` уже даёт для `config_backups`/`sync_logs`).
3. Страница/раздел сверки: для каждой активной `RegulatorEntry` — есть ли
   её `match_value` в снимке firewall (по `kind`: ip → `BLOCK_BY_IP_2`,
   fqdn/url-домен → `BBDNS_1`). Подсветить расхождения в обе стороны
   (регулятор велел, но не применено // применено, но регулятор не
