# ACL Lookup — дизайн (реализовано)

Статус: **реализовано** в этой сессии (не под git — репозиторий `NETBOX/` не
инициализирован как git-репо, поэтому коммита нет; этот файл — единственная
запись решения).

## Контекст и почему не через NetBox

Изначальная задача — загрузить ACL с Cisco ASR (`10.1.101.2`/`10.1.101.3`,
конфиги сохранены `netbox-sync/netbox_config_backup.py` в
`config_backups/<device>/latest.cfg`) в NetBox через плагин `netbox-acls`.
От этого отказались: у модели плагина (`ACLStandardRule`/`ACLExtendedRule`)
поля `source`/`destination` — не текст, а `GenericForeignKey` на реальные
объекты `ipam.Prefix`/`IPAddress`/`IPRange`/`Aggregate`. У двух ASR
обнаружились:
  - гигантский deny-блэклист `access-list 20` (~32к записей на каждом),
  - `object-group RusNets`, используемый в реально применённом ACL
    `Permit-Rus-Nets` — тоже ~9200 записей на каждом устройстве.

Загрузка в NetBox означала бы создание десятков тысяч новых Prefix-объектов
в общем IPAM, которым пользуется `ip_plan_docker` (`list_prefixes()` там не
поддерживает вообще никакой фильтрации — см. `netbox_client.py`). Даже с
тегом-исключением (`tag__n=acl`, протестирован и работает в NetBox 4.6) это
десятки тысяч мёртвых объектов ради статичного анализа конфига.

**Решение:** отдельная страница внутри `ip_plan_docker`, которая читает и
парсит `.cfg` напрямую, ничего не пишет в NetBox.

## Архитектура

```
config_backups/<device>/latest.cfg  (bind-mount, ro)
        │
        ▼
ip_plan/services/cisco_acl.py   — чистый парсер (текст → dataclasses)
        │
        ▼
ip_plan/services/acl_store.py   — кэш в памяти процесса, инвалидация по mtime
        │
        ▼
views.acl_lookup / views.acl_search  →  templates/ip_plan/acl_lookup.html
```

Никаких Django-моделей/миграций/БД для самих ACL — сознательное отступление
от общего принципа проекта («нет своих моделей для сетевых данных, всё через
NetBox API») в пользу «файл в памяти, как os_catalog.json», а не полноценной
БД: 82к правил линейно сканируются за ~18мс на поиск, индексы не нужны.

## Решённые вопросы (Q&A с пользователем)

1. **Источник данных** — только авто из `config_backups/*/latest.cfg`, без
   ручной загрузки файла в v1.
2. **Главный сценарий поиска** — «какой ACL трогает этот IP» (не текстовый
   grep по таблице).
3. **Хранение** — в памяти процесса с mtime-инвалидацией, без БД.
4. **Направление поиска** — и source, и destination (у extended ACL IP может
   быть с любой стороны правила).
5. **Прод-топология** — `netbox-sync` и `ip_plan_docker` предполагаются на
   одном хосте (v1); bind-mount `../netbox-sync/config_backups:/app/config_backups:ro`.
   Если это не так — нужна отдельная доставка файлов (не реализовано).

## Грамматика ACL

Проверена построчно на реальных данных (`grep`+`sed` по обоим `latest.cfg`)
перед написанием парсера — вместо попытки поддержать весь синтаксис Cisco
IOS ACL, парсер покрывает ровно то, что встречается:
  - именованные (`ip access-list standard|extended NAME`) и однострочные
    numbered (`access-list N permit|deny ...`) ACL;
  - `object-group network` (включая резолв в правилах через
    `object-group NAME`), без вложенности (`group-object` не встречается);
  - `any` / `host X` / `X wildcard` / голый `X` (implicit host);
  - протокол `ip|tcp|udp`, порт только `eq <port|mnemonic>` и `range A B`
    (`gt/lt/neq` не встречаются);
  - применение ACL: `ip access-group` (интерфейс), `access-class` (line
    vty), `snmp-server community ... RO/RW N`, `ip nat ... list NAME`.

Несмежные ("discontiguous") wildcard-маски — не поддерживаются (в данных
встретилась одна: `TELNET_ACCESS` на обоих ASR, `172.0.0.0 0.16.255.255`,
похоже на опечатку — должно быть `0.15.255.255` для /12). Такое правило
помечается `resolved=False`, не участвует в поиске, но видно в обзоре ACL —
полезный побочный эффект: инструмент выявил вероятную ошибку в реальном
конфиге.

## UI

- `/acl/` — форма поиска (HTMX, `hx-push-url` → `?ip=...` в адресной строке)
  + таблица результатов + обзорная таблица всех загруженных ACL (устройство,
  тип, число правил, применён/нет и где).
- Сортировка результатов: применённые ACL выше неприменённых; конкретные
  совпадения выше catch-all `permit/deny ip any any` (иначе такие строки
  забивали бы верх при любом запросе — по данным они реально совпадают с
  любым IP).
- Вход — иконка 🛡 рядом с «Экспорт в Excel» на главной странице IP-плана.

## Проверено

- Парсер — на обоих реальных `latest.cfg` (73 609 правил суммарно с учётом
  `object-group RusNets`), поиск ~18мс.
- Полный проход через Django test client (`force_login`, реальные
  шаблоны): `/acl/` (200, 21 строка обзора), `/acl/?ip=...` (200),
  `/acl/search/?ip=...` (HTMX-partial, 200), невалидный IP (понятная ошибка,
  не 500), IP, совпадающий только с "плохим" wildcard-правилом (0 крашей,
  корректно не засчитан).
- `docker compose up -d --build` — чистый старт, `config_backups` виден
  внутри контейнера.

## Добавлено позже: страница деталей одного ACL

`/acl/<device>/<acl_name>/` — полное содержимое одного ACL (все правила, включая
`remark`) в таблице. Вход — клик по имени ACL в обзорной таблице на `/acl/`.
Обратная ссылка «← ACL» ведёт на `/acl/?device=<device>` (сохраняет фильтр).

Поиск на этой странице — **не** тот же движок, что IP-lookup на `/acl/`
(не resolve source/destination в сети, не сортировка по catch-all) — здесь
это штатный built-in global-search DataTables (уже завендорен в проекте,
используется на главной таблице IP-плана). Выбор осознанный: для ACL "20"
(32202 правила) сервер рендерит все строки одним проходом (~1.2с, ~10MB
HTML — проверено), а дальше пагинация/сортировка/фильтрация — целиком на
клиенте, без повторных round-trip на каждый введённый символ. Протестировано
вживую в браузере на этом самом ACL — поиск мгновенный, ошибок в консоли нет.

404 (не 500) на несуществующее устройство или ACL — `Http404` в `acl_detail()`.

## Добавлено позже: object-group network как первоклассная сущность

`cisco_acl.py` парсил `object-group network` с самого начала (нужно было
для резолва `object-group NAME` внутри правил ACL — см. `Permit-Rus-Nets`),
но сами группы нигде не были видны отдельно от ACL, которые их используют.
Добавлено:

- `acl_store.list_object_groups(device_name=None)` / `get_object_group(device, name)`
  — те же device-фильтр и общий контекст, что и у ACL; `used_by` считается
  сканированием `Endpoint.kind == "object-group"` по всем правилам устройства.
- Секция «Все object-group network» на `/acl/` (та же таблица-паттерн, что
  у ACL: устройство/имя/размер/используется-где, с фильтром по устройству).
- `/acl/<device>/object-group/<name>/` — детали одной группы, тот же
  DataTables-паттерн (built-in search), что и у `acl_detail`. URL-префикс
  `object-group/` перед именем — чтобы не путать с `/acl/<device>/<acl_name>/`
  (Django матчит по количеству сегментов, коллизий с именами ACL нет, но
  человеку так яснее в адресной строке).

Проверено вживую в браузере: `RusNets` (9168 адресов, /22-/14 подсети из
netmask-формата object-group, верно отличается от wildcard-формата в самих
ACL-правилах) — открылась, поиск `2.60.0.0` мгновенно дал 1 совпадение
(`2.60.0.0/14`), обратная ссылка на ACL `Permit-Rus-Nets` кликабельна,
`Bots` на ASR2 корректно помечен «не используется» (ни в одном ACL). Консоль
чистая.

## Не реализовано / вне v1

Ручная загрузка файла, история версий ACL на UI (физически есть на диске —
timestamped `.cfg` от `netbox_config_backup.py`, просто не показывается),
IPv6, доставка `config_backups` между хостами при раздельном размещении
`netbox-sync`/`ip_plan_docker` в проде.
