# Редактирование конфигов netbox-sync из раздела "Настройки"

Дата: 2026-09-07

## Задача

Дать возможность править настройки подключения к оборудованию (добавлять
устройства, менять адреса/логины/пароли) через веб-интерфейс ip_plan, без
ручного редактирования JSON-файлов netbox-sync по SSH на прод-хосте.

Речь про файлы в корне netbox-sync, которые читают скрипты синка:

| Файл | Что внутри | В объёме UI |
|------|-----------|-------------|
| `devices.json → devices` | 8 устройств: host/port/username/password/model/site/флаги | да, полный CRUD |
| `devices.json → device_types` | 5 профилей моделей: CLI-команды, парсер, crypto-алгоритмы | да (см. ограничения ниже) |
| `config.json` | dns_servers, dns_skip_pattern, scan_exclude_prefixes, environments (URL+токен NetBox) | частично |
| `sources_redvirt.json`, `sources_vcenter.json` | 10 + 1 источник гипервизоров: name/url/user/password | да, CRUD списка |
| `config/ldap_settings.json` | FreeIPA bind DN/серверы **для netbox_dns_enrich.py** | **нет** — правится файлом |

Отдельно, уже не про netbox-sync, а про сам ip_plan (см. раздел
"Аутентификация" ниже): в объём входит управление **своим** LDAP-подключением
(`ip_plan/ldap_settings.json`) и локальные учётные записи. Это два РАЗНЫХ
LDAP-конфига: у netbox-sync свой (`config/ldap_settings.json` + `config/.env`,
нужен `netbox_dns_enrich.py` для CNAME-поиска), у ip_plan свой (вход в
интерфейс). Правка одного не влияет на другой — это стоит помнить, чтобы не
искать потом, "почему поменял, а не применилось".

Работы затрагивают два независимых git-репозитория: `ip_plan_docker_react`
и `netbox-sync` (у каждого свой GitLab-проект и свой CI).

## Решения (обсуждены и подтверждены с пользователем)

1. **Владение файлами: конфиги уходят из git netbox-sync.** Реальные
   `devices.json`/`config.json` живут только на прод-хосте (`/opt/scan`),
   в git остаются `*.example.json` без секретов. Причина — блокер, см.
   следующий раздел. Побочный выигрыш: пароли от xFW/Eltex/ASR/Maipu
   перестают лежать открытым текстом в GitLab.
2. **Объём:** `devices.json` (devices + device_types), безопасное
   подмножество `config.json` и оба `sources_*.json` (гипервизоры).
   Единственный конфиг вне объёма — `config/ldap_settings.json`.
3. **Доступ:** отдельная LDAP-группа FreeIPA (напр. `netbox-admins`) →
   `is_staff`. Текущая `netbox-users` (все, кто вообще входит в ip_plan)
   доступа к разделу не получает — там пароли от сетевого периметра.
4. **LDAP-подключение самого ip_plan правится из UI**, с обязательной
   проверкой bind'ом до сохранения.
5. **Появляется локальный вход** — учётка `admin`/`admin`, создаётся
   автоматически при первом старте, пароль меняется из UI и сменить его
   обязательно при первом входе. Это одновременно и требование, и
   страховка: без локального входа UI-управление LDAP — это способ
   заблокировать себе доступ намертво одной неудачной правкой.

## Блокер, ради которого нужна фаза 0

`devices.json`, `config.json`, оба `sources_*.json` и
`config/ldap_settings.json` сейчас **закоммичены** в git netbox-sync, а джоба `deploy_prod` делает
`rsync -a --delete-after` рабочего дерева в `/opt/scan`. Значит без фазы 0
любая правка из UI живёт до ближайшего пуша в `main` — потом её молча
затирает деплой. Это ровно тот же класс ошибки, что уже ловили с
`config_backups` (см. `2026-09-04-netbox-sync-log-viewer-design.md`).

Фаза 0 в netbox-sync — **реализована** (не закоммичена, см. "Состояние"):

1. `conf_loader.py` — `conf_path(name)`: сначала `conf/<имя>`, при
   отсутствии — историческое расположение в корне. Fallback нужен для окна
   между выкаткой этой версии и миграционным шагом деплоя.
2. Все четыре конфига перенесены в `conf/` и убраны из git
   (`git rm --cached`, записи в `.gitignore` закрывают и корень, и
   `conf/`). Рядом — четыре `conf/*.example.json` со значениями-заглушками;
   проверено программно, что ни одно реальное значение в примеры не
   утекло. `device_types` в примере перенесены вербатим — секретов там
   нет, зато это единственная документация того, какие профили моделей
   вообще поддержаны кодом.
3. 12 скриптов переведены на `conf_path()` (общего загрузчика раньше не
   было, каждый открывал файл сам). У трёх после этого осиротели `_base` и
   `from pathlib import Path` — убраны.
4. `.gitlab-ci.yml`: четыре `--exclude` (без ведущего слэша — закрывают оба
   расположения) плюс идемпотентный шаг миграции после rsync: корневой
   файл переезжает в `conf/`, только если там ещё пусто (иначе затёр бы
   правку из веб-интерфейса).
   **Порядок безопасен именно как один коммит**: пайплайн берёт `.gitlab-ci.yml`
   из того же коммита, поэтому `--delete-after` уже видит `--exclude` и не
   удаляет рабочие конфиги на проде.

Отдельным решением остаётся чистка git-истории (пароли лежат в старых
коммитах) и ротация паролей оборудования — в фазу 0 не входит, пока не
сделано, до тех пор пароли считать скомпрометированными.

`config/ldap_settings.json` UI не редактирует, поэтому он остаётся в git и
приезжает деплоем как раньше. Но рядом с ним в git лежит и `config/.env` —
**bind-пароль FreeIPA закоммичен**. Из UI этот файл не правится, так что для
самой задачи это ничего не меняет, однако по секретам это ровно та же
проблема, что решает фаза 0 для остальных четырёх конфигов. Вынести его тем
же способом (`git rm --cached` + `--exclude` в rsync + разово засеять на
проде) — отдельное решение, в объём этой задачи не входит.

## Архитектура

### netbox-sync: куда кладём редактируемые конфиги

Отдельные файлы bind-mount'ить в контейнер нельзя — атомарная запись
(`tmp` + `os.replace`, как в `services/os_catalog.py`) на bind-mount файла
ломается, нужен mount директории. Варианты:

- **(a) Смонтировать корень netbox-sync rw** + белый список имён файлов на
  уровне приложения. Ноль правок в netbox-sync, но контейнер технически
  может писать в код синка, который туда же деплоит CI.
- **(b) Перенести редактируемые конфиги в `netbox-sync/conf/`** (рядом с
  уже существующим `config/` для LDAP), добавить `conf_loader.py` с
  fallback на старый путь, монтировать rw только `conf/`. Скрипты правятся
  по 2 строки каждый (сейчас у каждого свой `open(_base / "...json")` —
  7 мест, общего загрузчика нет).

Берём **(b)**: контейнер физически не может писать никуда, кроме конфигов,
а загрузчик всё равно нужен для валидации. Fallback на старый путь делает
переход безопасным (прод продолжает работать, пока файлы не переехали).

### ip_plan_docker_react: чтение и запись

- **`ip_plan/services/sync_config.py`** — единственный модуль, который
  трогает файлы netbox-sync на запись. Отвечает за:
  - загрузку/сохранение с атомарной записью (`tmp` + `os.replace`), как в
    `os_catalog.py`;
  - ротацию версий: перед записью — копия в `conf/.history/devices.json.<ts>`,
    хранить N последних (откат в один клик; в отличие от `os_catalog.json`,
    где backup-файл один);
  - маскирование паролей на чтение (наружу отдаётся `"***"`, никогда
    реальное значение) и merge-on-write (пустое поле = оставить как было);
  - валидацию (см. ниже);
  - optimistic locking: клиенту отдаётся sha256 файла, на записи сверяется —
    два админа не затирают друг друга;
  - проверку `.full_sync.lock` — если прогон синка идёт прямо сейчас,
    показываем предупреждение (запись всё равно атомарна, но админ должен
    понимать, что текущий прогон может уже работать со старой версией).
- **`config/settings.py`**: `NETBOX_SYNC_CONF_DIR` — тот же принцип, что у
  `ACL_CONFIG_BACKUPS_DIR`/`SYNC_LOGS_DIR` (путь внутри контейнера, дефолт
  `BASE_DIR / "netbox_sync_conf"`).
- **`docker-compose.yml`**: `${NETBOX_SYNC_DIR:-../netbox-sync}/conf:/app/netbox_sync_conf`
  — **единственный не-`:ro` mount из netbox-sync**, рядом с тремя
  существующими read-only. Контейнер работает от root (в Dockerfile нет
  `USER`), файлы получатся root-owned; крон читает их из-под root — ок,
  а CI-раннер (gitlab-runner) их не трогает, т.к. они в `--exclude`.

### Права доступа

`ip_plan/ldap_config.py` сейчас знает только `AUTH_LDAP_REQUIRE_GROUP`.
Добавляется отображение групп FreeIPA на флаги
(`AUTH_LDAP_USER_FLAGS_BY_GROUP`) и декоратор `staff_member_required`-
эквивалент на все `/settings/*` вью. Модель прав двухуровневая: `is_staff` —
оборудование/гипервизоры/скан, `is_superuser` — LDAP, локальные учётки и
токен NetBox. Суперюзер проходит по `is_staff` автоматом. Подробности,
включая то, откуда берутся DN этих групп после фазы 4 — в разделе
"Аутентификация" ниже.

### UI

Существующие "Настройки" — dropdown в шапке (тема + сводка netbox-sync).
CRUD по устройствам туда не влезает: делаем **отдельную страницу
`/settings/`** (как `/acl/` и `/regulator/`), в dropdown добавляется ссылка
"Все настройки →" (видна только `is_staff`). Механика форм — ровно как у
`os_catalog_manage`: страница со списком + HTMX-модалки add/edit/delete,
партиалы в `templates/ip_plan/`, без перезагрузки страницы.

Вкладки:

1. **Оборудование** (`devices.json → devices`) — таблица 8 устройств,
   модалка на добавление/правку: host, port, username, password,
   `enable_password`, model (`<select>` из ключей `device_types`), site,
   status, чекбоксы `sync_interfaces`/`import_vlans`/`import_prefixes`/
   `sync_macs`/`backup_config`/`sync_blocklist`, `blocklist_objects`
   (пары ключ→имя объекта, показывать только при `sync_blocklist`).
2. **Модели** (`devices.json → device_types`) — CRUD профилей, но с
   жёсткими ограничениями, потому что часть полей завязана на код синка:
   - `interfaces_parser` — **только `<select>`** из 4 реализованных
     значений: `xfw`, `eltex_status`, `cisco_ios`, `maipu`
     (`netbox_devices_sync.py:1559-1570`); свободный ввод = молча
     пропущенный шаг "Interfaces";
   - `sync_macs` — доступен только при парсере `eltex_status`/`maipu`
     (`_mac_dispatch`, `netbox_devices_sync.py:1574`), иначе форма его
     запрещает;
   - удаление профиля запрещено, если на него ссылается устройство;
   - предупреждение в шапке вкладки: команды/crypto-алгоритмы — экспертные
     поля, ошибка здесь ломает шаги 2-5 full_sync.sh для всех устройств
     этой модели.
3. **Гипервизоры** (`sources_redvirt.json`, `sources_vcenter.json`) — два
   списка на одной вкладке, форма одинаковая: `name`, `url`, `user`,
   `password`. Файлы — плоские JSON-массивы, порядок элементов сохраняем
   (скрипты обходят их по порядку). Валидация: `name` уникален в пределах
   файла, `url` — `https://`, для RedVirt дополнительно предупреждение,
   если путь не оканчивается на `/ovirt-engine/api` (все 10 текущих
   источников такие — это API-эндпоинт, а не адрес веб-морды).
   Удаление источника из UI НЕ трогает уже заведённые в NetBox ВМ этого
   кластера: удаление "призраков" делает сам скрипт синка и только для
   кластеров, реально встреченных в прогоне — то есть исчезнувший из
   конфига источник просто перестаёт обновляться. Это надо написать прямо
   в диалоге удаления, иначе поведение неочевидно.
4. **Скан и DNS** (`config.json`) — `dns_servers` (список),
   `dns_skip_pattern`, `scan_exclude_prefixes` (список CIDR).
   `environments.{local,prod}` — URL показываем, токен только маской;
   правка блока `environments` — отдельная секция, видна только
   `is_superuser`.
5. **LDAP** (`LdapConfig`, только `is_superuser`) — серверы, bind DN и
   пароль, базы и фильтр поиска, `require_group`, группы для
   `is_staff`/`is_superuser`, выключатель `enabled`. Кнопки "Проверить
   подключение" и "Проверить вход пользователя". Путь к CA-сертификату —
   с пометкой, что смена требует перезапуска контейнера. См. раздел
   "Аутентификация".
6. **Пользователи** (только `is_superuser`) — локальные учётки: создать,
   удалить, выдать `is_staff`/`is_superuser`, сбросить пароль.
   LDAP-пользователи в этом списке показываются, но только для справки —
   они правятся в FreeIPA.
7. **netbox-sync** — существующая сводка последнего прогона, переезжает
   сюда целиком (в dropdown остаётся компактный вариант).

Смена собственного пароля — отдельная страница, доступная любому локальному
пользователю без `is_staff` (ссылка рядом с именем в шапке).

### Валидация (сервер, до записи)

Битый `devices.json` роняет шаги 2-5 full_sync.sh целиком, поэтому
валидация не опциональна:

- имя устройства уникально, непустое, без пробелов;
- `model` существует в `device_types`;
- `host` — валидный IP или FQDN; `port` — int 1..65535;
- `interfaces_parser` из белого списка (см. выше);
- `sync_blocklist: true` требует непустой `blocklist_objects`;
- `backup_config: true` требует `config_command`;
- элементы `scan_exclude_prefixes` парсятся `ipaddress.ip_network`;
- итоговый документ повторно сериализуется и парсится перед `os.replace`.

### Аудит

Модель `SettingsAudit` в SQLite ip_plan (модели там уже есть —
`migrations/0002_firewallobjectname.py`): кто, когда, что именно (файл
netbox-sync / LDAP-конфиг / локальная учётка), объект, поле, старое→новое.
Значения полей с паролями — `***`, никогда не пишем реальное значение даже
в журнал. Показывается на отдельной вкладке страницы настроек. Плюс версии
файлов в `conf/.history/` как физический откат для конфигов netbox-sync.

## Аутентификация: LDAP из UI + локальные учётки

Сейчас вход только через FreeIPA, настройки читаются из
`ip_plan/ldap_settings.json` **один раз при старте процесса** (файл
импортируется в `config/settings.py` через `from ip_plan.ldap_config import *`),
а сам файл лежит внутри образа — не bind-mount. То есть править его из UI в
текущем виде нельзя дважды: запись потерялась бы при пересборке контейнера, и
всё равно не применилась бы без рестарта.

### Где хранятся настройки

Модель-синглтон `LdapConfig` в SQLite (том `sqlite_data`, переживает
`up -d --build`). Поля — один в один текущий JSON: `servers` (список),
`bind_dn`, `bind_password`, `user_search_base`, `user_search_filter`,
`group_search_base`, `require_group`, `staff_group`, `superuser_group`,
`cache_timeout`, плюс `enabled` (глобальный выключатель LDAP).

Почему БД, а не файл, хотя для netbox-sync мы выбрали ровно наоборот: у
конфигов netbox-sync есть второй потребитель — процессы синка на том же
хосте, им нужен именно файл. У LDAP-настроек потребитель ровно один — это
самое Django-приложение, и файл здесь дал бы только лишний mount.

`bind_password` шифруется Fernet-ключом, производным от `SECRET_KEY`
(`cryptography` уже есть в образе как транзитивная зависимость — при
реализации вписать её в `requirements.txt` явно, полагаться на транзитивную
нельзя). Это защита от случайного просмотра БД, не от рута на хосте.

**Бутстрап**: data-миграция при первом `migrate` заполняет строку из
существующих `ip_plan/ldap_settings.json` + `LDAP_BIND_PASSWORD` из `.env`.
Прод после выкатки продолжает работать ровно как раньше, без ручных шагов;
файл дальше остаётся только сидом и аварийным образцом.

### Как применяется без рестарта

`ip_plan/auth_backends.py` — `DbLDAPBackend(LDAPBackend)`, переопределяющий
property `settings`: строит `LDAPSettings` и подменяет атрибуты значениями из
`LdapConfig`. Это опирается на устройство django-auth-ldap 4.8, проверенное
по исходникам в работающем контейнере: `LDAPBackend.settings` — property с
сеттером и ленивым `_settings` **на экземпляре**, а `django.contrib.auth`
создаёт новый экземпляр бэкенда на каждый вызов `authenticate()`. Значит
кеша между логинами нет и инвалидировать нечего. При обновлении
django-auth-ldap это место надо перепроверять — оно про внутренности
библиотеки, а не про публичный API.

Если `LdapConfig.enabled = False`, бэкенд возвращает `None` сразу, не
открывая соединение.

**Что так применить нельзя**: `AUTH_LDAP_GLOBAL_OPTIONS` — CA-сертификат
(`OPT_X_TLS_CACERTFILE`) и режим проверки. `OPT_X_TLS_*` в python-ldap
глобальны для процесса и должны быть выставлены до первого соединения (это
уже отмечено комментарием в текущем `ldap_config.py`). Поэтому смена
CA-сертификата остаётся файловой операцией + перезапуск контейнера, и UI
должен честно это писать рядом с полем, а не делать вид, что применилось.

### Локальные учётные записи

`ModelBackend` в `AUTHENTICATION_BACKENDS` уже есть — то есть локальный вход
технически работает уже сейчас, просто пользователя никто не создавал и
менять пароль неоткуда. Добавляется:

- **Модель `LocalAccount`** (OneToOne к `User`): `must_change_password`,
  кем и когда создан. Нужна, чтобы отличать локальные учётки от зеркал
  LDAP-пользователей, которые django-auth-ldap кладёт в ту же таблицу
  `auth_user`.
- **Команда `ensure_local_admin`** в `entrypoint.sh` после `migrate`:
  создаёт `admin` с паролем `admin`, `is_staff=is_superuser=True`,
  `must_change_password=True` — **только если локальных учёток нет вообще**.
  Повторные старты ничего не трогают, пароль не сбрасывают. Имя и пароль
  переопределяются переменными `LOCAL_ADMIN_USERNAME`/`LOCAL_ADMIN_PASSWORD`,
  а `SEED_LOCAL_ADMIN=false` отключает засев целиком.
- **Принудительная смена пароля**: middleware редиректит пользователя с
  `must_change_password=True` на страницу смены пароля отовсюду, кроме неё
  самой и logout. Пока пароль `admin`/`admin` не сменён, приложением
  пользоваться нельзя — иначе дефолтная учётка в проде живёт вечно.
- **Смена пароля** — `django.contrib.auth.views.PasswordChangeView` со своим
  шаблоном, доступна любому локальному пользователю (не только staff).
  LDAP-пользователю вместо формы показываем текст "пароль меняется в
  FreeIPA": его пароль тут не хранится (у зеркала `set_unusable_password`).
- **Вкладка "Пользователи"** (только `is_superuser`): создать/удалить
  локальную учётку, выдать `is_staff`/`is_superuser`, сбросить пароль.
  Пароли хранит Django своим хешированием (PBKDF2), в открытом виде нигде
  не появляются.

### Порядок бэкендов и защита от самоблокировки

`ModelBackend` ставится **первым**, `DbLDAPBackend` — вторым. Причина
практическая: в `AUTH_LDAP_GLOBAL_OPTIONS` стоят таймауты по 15 секунд на
сервер, и при недоступном/сломанном LDAP вход локального админа при обратном
порядке ждал бы эти таймауты по обоим серверам — ровно в тот момент, когда
локальный вход и нужен.

Побочный эффект порядка: локальная учётка с тем же именем, что у
LDAP-пользователя, перекрыла бы его. Поэтому при создании локальной учётки
проверяем, что такого uid нет в LDAP, и предупреждаем.

Остальные предохранители:

- Сохранению настроек LDAP предшествует **тестовый bind** с введёнными
  значениями (кнопка "Проверить подключение" делает то же самое явно).
  Не прошёл — не сохраняем; обойти можно только явной галочкой
  "сохранить всё равно".
- Дополнительно "тестовый вход": проверить конкретного пользователя —
  находится ли поиском и проходит ли `require_group`. Это ловит самую
  частую ошибку конфигурации: bind проходит, а логин нет.
- Выключение LDAP (`enabled = False`) запрещено, если в системе нет ни
  одной локальной учётки с `is_superuser` — иначе последним действием можно
  закрыть вход всем.
- Все изменения — в `SettingsAudit`.

### Права

- `is_staff` — оборудование, гипервизоры, скан и DNS.
- `is_superuser` — LDAP-подключение, локальные учётки, токен NetBox.
- Смена собственного пароля — любой локальный пользователь.

Отображение групп FreeIPA на флаги (`staff_group`/`superuser_group` →
`AUTH_LDAP_USER_FLAGS_BY_GROUP`) тоже становится полем в `LdapConfig`, а не
константой в коде.

### Порядок внедрения важен

Локальный вход делается **раньше**, чем UI для LDAP. Иначе первая же
неудачная правка LDAP из интерфейса оставляет всех снаружи, и чинить это
придётся через `manage.py` в контейнере на проде.

## Риски и открытые вопросы

- Правка через UI применяется не сразу, а на **следующем прогоне крона**
  (`0 3 * * *`) — это нужно явно написать в UI, иначе админ будет ждать
  эффекта немедленно. Кнопка "запустить синк сейчас" из UI — отдельная
  задача (нужен root, а контейнер к хостовому крону доступа не имеет).
- Старое приложение `ip_plan_docker` (HTMX, порт 8050) в объём не входит —
  живой стенд это `ip_plan_docker_react` (8090), подтверждено.
- Учётка `admin`/`admin` — заведомо слабый дефолт. Принудительная смена при
  первом входе обязательна именно поэтому; без неё она проживёт в проде
  годами. Отдельно стоит подумать про защиту от перебора на локальном
  входе (django-axes или ограничение на уровне nginx) — в объём не входит,
  но для учётки с `is_superuser` это уместно.
- `DbLDAPBackend` опирается на внутреннее устройство django-auth-ldap 4.8
  (property `settings`, отсутствие кеша между логинами). При обновлении
  библиотеки — перепроверять.
- Смена CA-сертификата LDAPS из UI невозможна без перезапуска контейнера
  (`OPT_X_TLS_*` глобальны для процесса в python-ldap).
- Пароли остаются в git-истории netbox-sync до чистки истории; до этого
  момента считать их скомпрометированными.

## Найденное попутно (исправлено в рамках фазы 1)

`config/settings.py` не задавал `AUTH_PASSWORD_VALIDATORS` вообще, а
дефолт самого Django — пустой список (набор из четырёх валидаторов живёт в
шаблоне `startproject`, которого у этого проекта не было). Пока вход был
только через FreeIPA, это ничего не значило — правила паролей задаёт
каталог. С локальными учётками проверять стало что, и первый же тест это
показал: пароль `123` принимался без единого возражения. Добавлены четыре
стандартных валидатора, `MinimumLengthValidator` с `min_length=10` вместо
дефолтных 8 — учётка не рядовая, у неё `is_superuser` и доступ ко всем
паролям сетевого периметра. `CommonPasswordValidator` заодно закрывает
возврат к `admin`: это слово есть в поставляемом с Django списке.

## Найденное попутно (фазы 2-3)

1. **`conf/.history/` не был закрыт ни `.gitignore`, ни `--exclude` в
   rsync.** Предыдущие версии конфигов содержат ровно те же пароли, что и
   сами конфиги, — то есть без правки они уехали бы в git при первом же
   `git add -A`. А `--delete-after` на проде стёр бы всю накопленную
   историю правок, потому что в CI-чекауте этой директории нет: та же
   ловушка, что уже ловили с `config_backups` и с самими конфигами.
   Добавлены `/conf/.history/`, `/conf/*.tmp` в `.gitignore` netbox-sync и
   `--exclude='conf/.history/'` в джобу деплоя.
2. **Имена версий с точностью до секунды теряли правки.** Два сохранения
   в одну секунду (правка и тут же исправление опечатки) писали в один и
   тот же файл истории. Добавлены миллисекунды.
3. **`user_passes_test` отправлял на страницу входа уже вошедшего
   пользователя.** Для человека, который залогинен, но не имеет
   `is_staff`, это выглядит как поломка входа. Заменено на свой декоратор:
   403 для обычных запросов и партиал ошибки для запросов из
   HTMX-модалки.

## Найденное при дизайн-проходе

1. **Модалки раздела были свёрстаны несуществующими классами.** Я
   использовал `modal-header` / `modal-body` / `modal-footer` и
   `btn-modal-danger`, а в проекте это `modal-title-bar` / `modal-body-pad`
   / `modal-footer-bar` и `btn-danger`. Правил под мои имена в `style.css`
   нет вообще — отсюда полное отсутствие отступов в окнах и неоформленные
   кнопки удаления. Все шесть форм переписаны на настоящие классы.
2. **`.set-field { flex: 1 1 240px }` ломал вертикальную раскладку.** В
   `.set-form` (флекс-колонка) `flex-basis` — это высота, а не ширина:
   каждое поле требовало 240 пикселей по вертикали, и форма LDAP
   разъезжалась пустотами. Правило ограничено `.set-form-row > .set-field`.
3. **Двухстрочный `{# … #}` рендерился как текст.** Комментарий Django в
   таких скобках однострочный (в регулярке лексера нет `re.DOTALL`) —
   многострочный уезжает в HTML как есть. Заменено на `{% comment %}`,
   остальные шаблоны проверены.
