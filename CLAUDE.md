# CLAUDE.md

Инструкции для Claude Code по работе с `ip_plan_docker_react` — отдельный
git-репозиторий (не часть монорепо `NETBOX/`). Общая карта репозитория и
правила, применимые ко всем трём подпроектам — в `../CLAUDE.md`.

> [!warning] До 2026-09-10 существовала более старая версия этого приложения
> без React — `ip_plan_docker` (удалена). Если где-то в документации/коде
> встречается путь `ip_plan_docker` или порт `8050` — это про неё, не про
> текущий репозиторий (порт здесь `8090`).

## Запуск локально

```bash
cd ip_plan_docker_react
cp .env.example .env          # заполнить SECRET_KEY, NETBOX_URL, NETBOX_TOKEN, NETBOX_SYNC_DIR
cp .env.db.example .env.db    # пароли PostgreSQL (см. «PostgreSQL и перенос с SQLite»)
docker compose up -d --build
docker compose logs -f web
```

`.env.db` обязателен: `docker-compose.yml` подключает его как `env_file` сервиса
`postgres`, и без файла compose не стартует вовсе. Пароли ролей в нём и в `.env`
(`IP_PLAN_DB_PASSWORD`, `NETOBS_RO_PASSWORD`) должны совпадать — подробности в
разделе про PostgreSQL ниже. `web` ждёт `postgres` по healthcheck, поэтому
первый старт на пустом томе занимает чуть дольше; по умолчанию приложение при
этом всё равно работает на SQLite (`IP_PLAN_DB_ENGINE` не задан).

Приложение доступно на `http://localhost:8090` (проброс `8090:8000`).

При каждом старте контейнера `entrypoint.sh` выполняет по порядку: ожидание
PostgreSQL (только при `IP_PLAN_DB_ENGINE=postgres`, до `DB_WAIT_SECONDS`, по
умолчанию 60 с) → `manage.py migrate` → `manage.py ensure_local_admin` (см.
ниже) → `manage.py collectstatic`, затем запускает `gunicorn`.

## Архитектура

Приложение — **не только** тонкий HTMX-фронтенд поверх NetBox REST API, как
было в старой (удалённой) версии. Основная таблица IP-адресов по-прежнему
устроена так — своих моделей для неё нет, всё читается/пишется напрямую через
NetBox API (`ip_plan/services/netbox_client.py`). Но за последнее время
появилось несколько подсистем с **настоящими Django-моделями и БД**
(`ip_plan/models.py`, `ip_plan/migrations/`, 13 миграций на 04.10.2026):

- **Реестр блокировок регулятора** (`RegulatorDocument`, `RegulatorEntry`,
  `FirewallObjectName`) — письма регулятора и их IP/FQDN/URL/IOC-записи
  накапливаются во времени, не проксируются через NetBox (см.
  `docs/plans/2026-09-04-regulator-blocklist-design.md`). Таблица записей на
  странице письма и вкладка «Записи» общего списка — React/TanStack-island
  (`ip_plan/static_src/regulator_table`), тот же принцип, что у основной
  IP-таблицы (`ip_plan/static_src/ip_table`): один fetch целиком, дальше вся
  фильтрация/сортировка/пагинация на клиенте.
- **Раздел «Настройки»** (`ip_plan/views_settings.py`, `ip_plan/templates/ip_plan/settings.html`
  и `_settings_*.html`) — редактирование конфигов netbox-sync через UI вместо
  ручной правки файлов на проде. Разделы и рейка — см. «Настройки v2»:
  Оборудование/Модели/Гипервизоры/Скан и DNS/Доступ к хостам (`is_staff`,
  правят `conf/devices.json`, `conf/sources_*.json`, `conf/config.json`,
  `conf/ssh_access.json`), Вход и LDAP/Пользователи (`is_superuser`),
  Журнал и Запуск и расписание (`is_staff`). Пишет
  файлы через `ip_plan/services/sync_config.py` — единственное место в
  приложении, которое имеет право писать в примонтированную `netbox-sync/conf`
  (атомарная запись tmp+rename, история версий в `conf/.history/` — до 20 на
  файл, хеш файла проверяется при сохранении, чтобы два администратора не
  затёрли правки друг друга молча; секреты в форму никогда не уходят в
  открытом виде — только маска `••••••••`, а сохранение маски как есть = «не
  менять»).

  Внутри раздела есть три подсистемы, о которых стоит знать до правок:

  - **Экспорт/импорт** (`ip_plan/services/settings_bundle.py`) — кнопки в шапке
    раздела. Экспорт отдаёт ZIP с `devices.json`, `sources_redvirt.json`,
    `sources_vcenter.json` (плюс опционально `config.json` и настройки входа).
    Импорт **дополняет**, а не заменяет: сначала предпросмотр «что добавится,
    что уже совпадает, где расхождения», существующие записи и пароли по
    умолчанию не трогаются. Рабочие данные (IP-адреса, блокировки, каталог ОС)
    в перенос не входят принципиально — смысл в том, чтобы на чистой установке
    быстро получить устройства, гипервизоры и доступы к ним.
  - **Проверка подключения** (`ip_plan/services/connection_test.py`, модель
    `ConnectionTest`) — кнопка ▶ у каждого устройства и источника: ICMP → TCP →
    SSH (или HTTP API у гипервизоров), ход проверки виден в модальном окне ▤.
    Идёт в отдельном потоке, состояние в БД, а не в памяти процесса: воркеров
    gunicorn несколько, и один SSH к недоступному устройству съедает весь
    `--timeout 60`. Запись «выполняется» старше `STALE_AFTER` считается
    сорванной перезапуском контейнера.
  - **Эффективные настройки в списке устройств.** Синк читает настройки
    устройства поверх настроек его модели (`_resolve` в
    `netbox_devices_sync.py`), и список должен показывать ту же картину:
    шаги-чипы считаются по объединению модель+устройство, а пришедшее от
    модели подписано отдельной строкой. Иначе получается, что в карточке
    «ничего не собираем», хотя сбор идёт — `sync_macs` и `sync_lldp` почти
    везде заданы на уровне моделей.

  **Парсеры и их возможности — из реестра платформ netbox-sync**
  (`registry/platforms.json`, с 04.10.2026). `INTERFACE_PARSERS`,
  `SNMP_PARSERS`, `MAC_CAPABLE_PARSERS`, `LLDP_CAPABLE_PARSERS` в
  `services/sync_config.py` остались именами модуля, но вычисляются из
  реестра (кэш по mtime — новая версия файла видна без перезапуска). Каталог
  `registry/` смонтирован в `web` только на чтение
  (`/app/netbox_sync_registry`, `NETBOX_SYNC_REGISTRY_DIR`); каталог, а не
  файл — смонтированный файл держит старый inode после `git checkout`.
  Нет реестра или он битый — `SyncConfigError`, тихого возврата к зашитым
  спискам нет (R5). Новый парсер в netbox-sync = правка реестра там же
  (контрактный тест netbox-sync сверяет его с диспетчерами); здесь править
  ничего не нужно. Включённый флаг на неподдерживаемом парсере форма
  по-прежнему не принимает.

  - **Раздел «SNMP» есть у каждого устройства** (30.09.2026), независимо от
    транспорта: версия (`snmp_version`: пусто / `v2c` / `v3`), порт,
    community-список для v2c (`snmp_communities` — у кластеров ViPNet первая
    адресует активную ноду, вторая пассивную) или пользователь и пароли для v3
    (`snmp_user`, `snmp_auth_*`, `snmp_priv_*`). Пустая версия чистит все
    `snmp_*`-ключи. `sc.snmp_version(cfg)` понимает и записи, сделанные до
    появления поля (по `snmp_user`/`snmp_communities`). У SSH-устройств
    заполненный раздел добавляет шаг **SNMP** в проверку подключения после
    SSH, и молчащий агент там — ошибка, а не пропуск; у SNMP-моделей раздел
    обязателен — по нему идёт весь сбор.
  - **Транспорт устройства задаёт парсер его модели** (`sc.transport()`:
    `SNMP_PARSERS = {"continent_snmp"}` → «snmp», остальное «ssh»). У
    SNMP-устройств в блоке подключения нет логина/пароля (реквизиты — в
    разделе «SNMP»), блок переключается в браузере при смене модели (Alpine,
    `model_transports`). `device_save` берёт ветку по транспорту и
    **вычищает ключи другой ветки**, чтобы в `devices.json` не копились
    мёртвые `username`/`cluster_*`. Для кластера Континента два поля:
    «Резервная платформа кластера» (`cluster_reserve`) у активной ноды и
    «Резерв для» (`cluster_peer_of`) у инвентарной записи резервной — у неё
    допустим пустой адрес, реквизиты не нужны, шаги сбора принудительно
    `false`. Проверка подключения для таких устройств: ICMP → SNMP GET
    (`_check_snmp`: sysName, sysDescr; v2c и v3); агент Континента молчит и
    на неверные реквизиты, и на адрес не из списка разрешённых хостов, так
    что текст шага перечисляет все три причины.
    Пакеты `puresnmp` + `puresnmp-crypto` — в `requirements.txt`, нужна
    пересборка образа.
- **Аутентификация** — двухбэкендовая: `ModelBackend` (локальные учётки) +
  `ip_plan.auth_backends.DbLDAPBackend` (свой LDAP-бэкенд поверх
  `django_auth_ldap.LDAPBackend`, переопределяющий `settings`-property так,
  чтобы читать параметры FreeIPA из модели `LdapConfig`, а не из
  `django.conf.settings` — иначе правка LDAP из UI требовала бы перезапуска
  контейнера). Единственное, что по-прежнему в `.env`/`settings.py`, а не в
  БД — путь до CA-сертификата LDAPS (`LDAP_TLS_CA_CERT`): опции TLS в
  python-ldap глобальны для процесса, меняются только файлом и перезапуском.
  `ip_plan/ldap_settings.json` теперь используется только как одноразовый
  сид для миграции `0008_seed_ldap_config` (переносит значения в БД при
  первом `migrate`, дальше не читается).

  Проверки LDAP из UI (`ip_plan/services/ldap_check.py`) ходят напрямую через
  python-ldap, мимо `django_auth_ldap`: они не должны ничего создавать в БД и
  работают со значениями из формы, ещё нигде не сохранёнными. Две грабли,
  которые там уже обезврежены и которые легко вернуть обратно:
  `OPT_X_TLS_NEWCTX` на соединении пересоздаёт TLS-контекст **из опций этого
  соединения**, а путь к CA у нас глобальный — новый контекст остаётся без
  него, и bind падает с `SERVER_DOWN: certificate verify failed`, хотя
  реальный вход в это же время работает; `ldap.filter` — отдельный подмодуль,
  при одном лишь `import ldap` обращение к `ldap.filter.escape_filter_chars`
  даёт `AttributeError`. Обе ошибки выглядели как «каталог недоступен», а
  сохранение настроек LDAP блокируется до успешного bind — то есть защита,
  ради которой всё писалось, была фактически выключена.
- **Локальный аварийный администратор** — `manage.py ensure_local_admin`
  (вызывается `entrypoint.sh` на каждом старте, но создаёт учётку **только
  если** локальных ещё нет; повторные старты пароль не сбрасывают). Нужен на
  случай неверной правки LDAP-настроек из UI: не должно быть сценария, где
  ошибка в интерфейсе оставляет снаружи вообще всех. `ip_plan.middleware.ForcePasswordChangeMiddleware`
  держит такую учётку на странице смены пароля, пока `LocalAccount.must_change_password`
  не снят — до этого приложение никуда больше не пускает.

БД Django — **PostgreSQL 18** (сервис `postgres` в `docker-compose.yml`, база
`ip_plan`) или, по умолчанию, SQLite (`data/db.sqlite3`, Docker volume
`sqlite_data`). Выбирает переменная `IP_PLAN_DB_ENGINE` (`sqlite` или `postgres`,
пусто = `sqlite`; любое другое значение — `ImproperlyConfigured` при старте,
чтобы опечатка не подняла приложение на SQLite молча). На `postgres` переключать
**только вместе с переносом данных** (раздел «PostgreSQL и перенос с SQLite»
ниже); откат — вернуть `sqlite` тем же способом, пока в PostgreSQL ничего не
писали. В базе — Django-сессии, LDAP-зеркалированные объекты `User` и все
модели выше — `RegulatorDocument`/`RegulatorEntry`/`FirewallObjectName`/
`LocalAccount`/`SettingsAudit`/`LdapConfig`/`ConnectionTest`. Второй базой того
же PostgreSQL — `netobs` (наблюдения MAC/IP, пишет netbox-sync) — ip_plan только
читает, см. «Поиск MAC/IP».

Прочее по-прежнему как было:
- `ip_plan/services/netbox_client.py` — класс `NetBoxClient`: единая
  HTTP-сессия, пагинация (`limit=1000`, `offset`), типизированная ошибка
  (`NetBoxAPIError` с `status_code`)
- `ip_plan/views.py` — все view возвращают HTML-партиалы (HTMX OOB swaps) или
  JSON. Никаких перезагрузок страницы при CRUD-операциях
- **CSRF для htmx** — токен отдаётся один раз через `hx-headers` на `<body>`
  в `base.html`. Без него работают только те запросы, что сидят внутри
  `<form>` с `{% csrf_token %}`: одиночная `hx-post`-кнопка получает 403, и
  снаружи это выглядит как «кнопка не нажимается», без единого сообщения
- `ip_plan/services/network_tools.py` — тонкие обёртки над `fping` и `nmap`
  (оба должны быть в контейнере)
- `ip_plan/services/os_catalog.py` — каталог ОС хранится в
  `admin/os_catalog.json` (bind-mount, редактируется на хосте)
- `column_info.json` — описания колонок таблицы IP, читается один раз при
  старте процесса; обновление требует пересборки контейнера

## Версия сборки

В правом нижнем углу каждой страницы (включая страницу входа — её видно без
авторизации) стоит номер версии: `v0.1`. По нему проверяют, доехал ли деплой:
если после выкатки номер прежний, значит контейнер не пересобрался.

Номер лежит в файле `VERSION` в корне репозитория, читается один раз при
старте процесса (`APP_VERSION` в `config/settings.py`) и попадает в шаблоны
через `ip_plan/context_processors.py`.

**Перед каждым деплоем номер поднимают на 0.1:**

```bash
./bump_version.sh          # 0.1 → 0.2
./bump_version.sh 1.0      # выставить конкретное значение
```

Файл `VERSION` коммитится вместе с остальными изменениями — иначе на проде
окажется старый номер и проверка потеряет смысл.

> [!warning] Стиль `.app-version` живёт в `style.css`, а не в `shell.css`/`nav.css`:
> страница входа подключает только первый. Положив его в `nav.css`, уголок
> получаешь без позиционирования — блок уезжает в середину страницы.

### Версия netbox-sync в сводке прогона

Рядом со сводкой последнего синка («Настройки» → блок `.sync-log-meta`)
показывается версия `netbox-sync`, на которой шёл прогон: `· sync v0.1`.
Свой `VERSION` у netbox-sync тоже есть, но приложение его файл не видит —
в контейнер монтируются только `conf/` и `sync_logs/`. Поэтому номер
передаётся **через заголовок лога**: `full_sync.sh` пишет
`[version=…]` в первую строку, `ip_plan/services/sync_log.py` вытаскивает
его регуляркой `_HEADER_RE` (группа необязательная — логи, снятые до
появления строки, парсятся по-прежнему).

С этапа 2 `full_sync.sh` выполняет только nmap, и версия из его лога —
версия ночного nmap. Задания сборщика несут свою (`SyncJob.code_version`);
сводка «Синк» показывает версию последнего задания цепочки ночи, а без
заданий — из лога nmap. Ручной копии списка шагов `full_sync.sh` в
`sync_log.py` больше нет: там один `NMAP_STEP` (тест сверяет его с
`full_sync.sh`, если netbox-sync лежит рядом), шаги заданий — из
`sync_jobs.STEPS_LIST`.

## Подключение к хосту из таблицы адресов (SSH / VNC / RDP / консоль ВМ)

Меню строки (⋯) → раздел «Подключиться». Подход — **локальные клиенты
пользователя, без шлюза и без хранения учёток на сервере**
(`static_src/ip_table/components/connect.js`):

- **SSH, VNC** — переход по `ssh://[user@]host` и `vnc://host`. macOS открывает
  Terminal и «Общий экран» сам; на Windows/Linux обработчик схемы надо
  зарегистрировать (PuTTY/KiTTY/Windows Terminal, RealVNC/TigerVNC, Remmina).
- **RDP** — на macOS ссылка `rdp://full%20address=s%3Ahost[&username=s%3Auser]`
  для Windows App (бывший Microsoft Remote Desktop; двоеточие после «=»
  обязательно `%3A`), на остальных платформах скачивается файл `.rdp`
  (`prompt for credentials:i:1`, без пароля) — его открывают mstsc, Windows
  App и Remmina.
- **Консоль ВМ** — пункт виден только у адресов с ролью `vm`. `POST
  /ip/<id>/console/` (`views.ip_console` → `services/vm_console.py`) находит
  ВМ в NetBox, по типу её кластера (`red-virt` / `vcenter`, slug'и из синков)
  выбирает гипервизор и спрашивает его теми же учётками, что у
  синхронизации (`conf/sources_redvirt.json`, `conf/sources_vcenter.json`):
  - RedVirt/oVirt: `POST …/graphicsconsoles/<id>/remoteviewerconnectionfile`
    → готовый файл `.vv` с одноразовым билетом для remote-viewer
    (virt-viewer); SPICE предпочтительнее VNC, выдаётся только у запущенной
    ВМ (иначе 409 с понятным текстом).
  - vCenter: легаси REST `/rest/vcenter/vm?filter.names=` → ссылка
    `vmrc://<vcenter>/?moid=<vm-id>` для VMware Remote Console. Билет
    клонирования сессии намеренно не берём — пользователь входит в VMRC
    под своей учёткой, а не под сервисной.
- Имена пользователей для SSH и RDP — меню «Вид» → «Подключение к хостам»,
  хранятся в браузере (`ip_table_v2_connect`), в сброс вида не входят.

### В браузере — шлюз Apache Guacamole (02.10.2026, только локальный стенд)

Локальные клиенты плохо ложатся на парк рабочих станций с разными
российскими ОС (обработчики `ssh://`/`vnc://`, remote-viewer, VMRC везде
настраиваются по-своему), поэтому рядом появился второй путь — сессия в
новой вкладке браузера. При включённом шлюзе в меню строки два раздела:
«В браузере» (действия `web-ssh` / `web-vnc` / `web-rdp` / `web-console`) и
«Локальный клиент» (всё прежнее). Исследование и варианты —
`docs/plans/2026-10-01-remote-access-gateway-research.md`.

- **Контейнеры** `guacd` и `guacamole` (1.6.0) — в `docker-compose.yml` под
  профилем `gateway`: обычный `docker compose up -d` и деплой из CI их не
  поднимают. Включение — `COMPOSE_PROFILES=gateway` и
  `GUACAMOLE_JSON_SECRET_KEY` в `.env`. Без ключа раздела «В браузере» нет
  (`window.IP_PLAN_GATEWAY`, context processor `shell`), эндпоинт отвечает 503.
- **Guacamole без базы данных**, расширение auth-json: пользователей и
  соединений в нём нет. `POST /ip/<id>/connect/` (`views.ip_connect` →
  `services/remote_gateway.py`) собирает JSON с одним соединением,
  подписывает и шифрует общим ключом, обменивает на токен
  (`GUACAMOLE_INTERNAL_URL`, сеть compose) и отдаёт адрес вкладки
  `GUACAMOLE_PUBLIC_URL/#/client/<id>?token=…`.
- **Адрес хоста — из NetBox по id записи**, не из запроса: шлюз ходит с
  адреса сервера, произвольный адрес через него открыть нельзя.
- **Пароли к хостам ip_plan не знает**: логин и пароль спрашивает Guacamole
  в своей вкладке; из браузера приходит только имя пользователя из меню
  «Вид» (для RDP `ДОМЕН\имя` режется на domain и username).
- **Консоль ВМ — только RedVirt**, по VNC: `vm_console.ovirt_vnc` берёт адрес
  и порт консоли (`graphicsconsoles?current=true`) и одноразовый пароль
  (`…/ticket`, 120 с). У всех запущенных ВМ MDC консоль VNC есть (проверено
  02.10.2026), так что отсутствие SPICE в Guacamole не мешает. ВМ на vCenter
  и ВМ только со SPICE получают 409 с подсказкой про локальный клиент.
- **Вкладка открывается до запроса к серверу** (`openGatewaySession` в
  `connect.js`): после `await` браузер счёл бы `window.open` всплывающим
  окном. При отказе сервера пустая вкладка закрывается, причина — в тосте.
- **Токен в адресе вкладки обязателен**: Guacamole хранит текущий токен в
  localStorage, общем для всех вкладок, и вторая сессия его заменяет;
  собственный токен в адресе даёт каждой вкладке пережить обновление.
- **Доступ — только staff** (`GUACAMOLE_STAFF_ONLY`, по умолчанию включено):
  шлюз даёт сетевую досягаемость с адреса сервера. Журнал — строка
  `Шлюз: <кто> открыл <протокол> к <хост>` в логе контейнера `web`.

Что не сделано для прода: `location /guac/` в nginx хоста (WebSocket upgrade)
и `GUACAMOLE_PUBLIC_URL`; строки `COMPOSE_PROFILES` / `GUACAMOLE_*` в `.env`,
который собирает `.gitlab-ci.yml`; согласование сетевого доступа (сейчас
подходит правило `NETBOX_SCAN` xFW MDC для `10.1.108.69`, но оно заведено
под сканирование); расширение `ban` Guacamole за прокси увидит всех с одного
адреса — нужен `RemoteIpValve` либо отключение. Сессия в drawer через iframe
— возможный следующий шаг, требует общего origin.

## Доступ к хостам по SSH: служебный ключ (02.10.2026)

«Настройки» → «Доступ к хостам» (`_settings_access.html`, views
`ssh_access_save/delete/test`, сервис `ip_plan/services/ssh_access.py`). Одна
служебная учётная запись и её закрытый ключ; файл —
`netbox-sync/conf/ssh_access.json` (`username`, `port`, `private_key`,
`passphrase`). Появился из исследования точности гостевых ОС
(`../research/guest-os/`): на старых ОС надёжно работает только простая
команда по SSH, а для неё нужен вход.

Кто пользуется ключом:

- **Проверка входа** на вкладке: `ssh_access.probe(host)` — TCP, вход, одна
  команда чтения (`os-release`, запасные `redhat-release`/`issue`, `uname`,
  `hostname`), результат — ОС, ядро, имя. С RSA-ключом при отказе вход
  повторяется со старой подписью (OpenSSH до 7.2 не умеет rsa-sha2).
- **Шлюз, пункт «SSH по ключу»** (`web-ssh-key` → `proto: ssh-key` в
  `views.ip_connect`): Guacamole входит служебной учёткой, пользователь
  ничего не вводит. Пункт виден, только когда шлюз доступен и ключ задан
  (`window.IP_PLAN_GATEWAY_KEY`). Обычный «SSH» с личным логином остался.
  Следствие, которое надо помнить: в журнале хоста все такие входы — один
  пользователь; кто именно открыл сессию, видно только в логе ip_plan.
- **Синк** — пока не пользуется: шаг опроса ОС на машинах не написан, файл
  лежит в `conf/` именно ради него.

Что отличает этот файл от остальных конфигов и что легко сломать:

- **Его нет в `sync_config.FILES`** — намеренно: реестр используют экспорт
  настроек и история версий, а копиям закрытого ключа в архивах и в
  `conf/.history/` делать нечего. Запись своя: атомарная, с проверкой хеша,
  права 0600, без истории.
- **Ключ в браузер не уходит никогда**, даже маской: страница показывает тип,
  отпечаток и открытую часть (для `authorized_keys`), пустое поле ключа при
  сохранении = «оставить прежний». В журнал настроек пишется отпечаток.
- **В Guacamole ключ уходит внутри зашифрованного JSON**, сервер-сервер.
  Пользователю Guacamole параметры соединения не отдаёт: запрос
  `…/connections/<id>/parameters` с его токеном — 403 (проверено).
- **Соседний репозиторий:** файл добавлен в `.gitignore` netbox-sync и в
  исключения `rsync` его `.gitlab-ci.yml`. Без первого закрытый ключ виден
  git как новый файл, без второго `--delete-after` стирает его на проде при
  каждом деплое.
- **Ключ хоста не проверяется** ни в проверке (paramiko `AutoAddPolicy`), ни
  в шлюзе (guacd: «host identity will not be verified») — как и у остальных
  SSH-соединений проекта.
- Парольную фразу paramiko от «не тот тип ключа» отличает плохо, поэтому
  `parse_key` сначала читает ключ без фразы (так он однозначно говорит
  «зашифрован»), и только потом с ней.

Форма стоит на странице, а не в модалке, поэтому при ошибочном ответе сама
открывает модальное окно (`hx-on::after-request`): партиал ошибки приходит в
`#modal-content`, и без этого рисуется в закрытое окно. С 02.10.2026 тот же
обработчик стоит у форм «Скан и DNS», «Вход и LDAP» и карточек устройства и
модели. Тесты: `ip_plan/tests/test_ssh_access.py`.

## Площадка в таблице IP-адресов

У IP-адреса в NetBox нет поля site — площадка у него всегда производная,
и считает её бэкенд (`views.py`): от устройства/ВМ, на которые адрес
назначен (`_attach_roles_bulk` → `_site`), иначе от самого специфичного
префикса с `scope_type=dcim.site` (`_attach_sites_from_prefixes`). В
`/ip/list.json` строка несёт `site` ({slug, name} либо null), список
`site_choices` — весь справочник `dcim/sites` (не «встречающиеся среди
адресов», как у ролей: список площадок обязан совпадать с настройками). Фильтр «Площадка»
в тулбаре React-таблицы стоит первым после поиска (`TableRoot.jsx`,
`siteFilter`); клиент только сравнивает slug, логики вывода площадки там
нет и быть не должно.

- **Группы хостов** (Server / Hypervisor / VM / СХД): по кластеру NetBox,

- **Фронтенд** — React-остров `ip_plan/static_src/topo_map` на

«Проверить трафик»); `acl/where/?q=<ip|cidr>&device=…` → `acl_where`

которых в снимке есть списки.
Старые шаблоны (`acl_lookup.html`, `_acl_page_body`, `_acl_search_results`,
`_acl_overview`, `_acl_object_groups`, `acl_detail.html`) удалены;
`_acl_snapshots.html` остался для страницы истории. Фильтры
`plural`/`ru_number` — в `ip_plan_extras`.

Две ловушки вёрстки, чтобы не наступить снова: класс `row` из макета
конфликтует с Bootstrap `.row` (строки разваливались) — у ACL свои классы;
любой ввод внутри `.drawer` оболочки ставит `$store.drawer.dirty`, и Esc
начинает спрашивать «Закрыть без сохранения?» — у панели группы на корне
стоят `@input.stop @change.stop`.

Как считается результат (`acl_search.search`):

- **Запрос** — IPv4-адрес или подсеть CIDR (`parse_query`; IPv6 — понятная
  ошибка). Для подсети совпадением считается и «запрос внутри сети правила»,
  и «сеть правила внутри запроса» (правило упоминает адрес из неё).
- **Части операнда** (`_parts`). `Endpoint.networks` плоский, поэтому операнд
  режется заново тем же `_split_refs`, что и в парсере ViPNet: литералы,
  `@объекты` (по словарю объектов устройства), узлы `0x…`, any. Сети узла
  (включая туннельные диапазоны из iplir) парсер теперь кладёт в
  `extra["{side}_node_nets"]` — без этого правила секции Tunnel терялись.
  Исключения объекта (ViPNet Exclusion) снимают совпадение.
- **Категория**: `exact` (адрес указан явно / хост внутри искомой подсети) →
  `net` (входит в подсеть правила) → `obj` (через объект) → `broad` (через сеть
  короче `ACL_WIDE_PREFIX`, по умолчанию /16: 10/8, 0/0, @PrivateNetworkIP) →
  `any` (совпало только через any). У правила берётся лучшая категория по
  сторонам; `broad` и `any` уходят в свёртки внизу, остальное — в группы
  устройство → список, внутри сортировка «точные выше». Роль адреса —
  src / dst / both по сторонам с не-any совпадением.
- **«Явный запрет»** — deny/drop только в категориях exact/net/obj: запреты
  через 10/8 или any явными не считаются (так в макете: «Явных запретов нет»
  при наличии drop-правил среди широких).
- **Цепочка «почему совпало»** — `[{value, note}]`: адрес → сеть → объект →
  вложенный объект (спуск по `object_group_includes` до того объекта, который
  реально содержит совпавшую сеть; у объектов — «N записей»), у узлов ViPNet —
  «узел ViPNet · имя».
- Подсчёт `any` честный: правило «X → any» подходит любому адресу как
  назначению, поэтому у чужого адреса счётчик any большой — это ожидаемо.

Шапка списка правил — крошки «ACL / устройство / раздел»: устройство и
кнопка «К выбору» ведут на главную с этим устройством в выборе
(`listing.back_url` = `/acl/?device=<имя>`); строки-сводки под шапкой нет,
секции ViPNet — подчёркнутые вкладки в стиле «Найти адрес» (`acl-q-tab`).

Список правил (`acl_search.listing`): строки трёх типов (`rule` с фрагментами
`text/any/group/hit`, `remark`, `collapsed` — блоки от 3 правил без совпадений
при заданном `?q=`), `match_text` («источник · через группу», «назначение ·
подсеть», «оба направления», «подходит любой адрес»), якоря `rule-<id>` для
навигации «1 из N». У списков ViPNet (`listing.is_firewall`) над таблицей
чипы-фильтры по действию (Все / pass / drop / NAT) и состоянию (Все /
включено / выключено) со счётчиками `action_counts`/`state_counts`;
фильтрация на клиенте по `data-action`/`data-inactive` (класс
`is-filtered`), навигация «N из M» идёт только по видимым совпадениям. У
ACL коммутаторов этих чипов нет: выключенных правил там не бывает.
Совпадением в списке считаются только exact/net/obj:
попадания через 10/8, 0/0 и any подписываются («источник · входит в /0»),
но в счётчик и подсветку не идут; в стикере-наборе совпавший элемент
выносится первым, чтобы не прятаться за «…». Совпадение через
туннелируемый диапазон координатора (строки `tunnel=` узла в iplir; парсер
кладёт узлы в `ParsedDevice.vpn_nodes`) — категория `net` с подписью
«источник · туннель узла», в цепочке «туннель lo-hi · за координатором», в
панели узла — чип «туннель lo-hi» и счётчик «туннели: N». Панель группы (`group_panel`): члены, содержащие адрес, —
первыми, затем вложенные группы и исключения («кроме»), первые 200. Объект из
узлов ViPNet (VPN-объект) показывается строкой на узел — имя из iplir, рядом
адреса «реальный → виртуальный», идентификатор `0x…` тегом, подсказка с
номером сети; плоский список /32 при этом не дублируется, а панель (drawer)
расширяется через `.drawer:has(.acl-panel.is-wide)`. Пары адресов узла
подписаны «реальный → виртуальный» (строки `ip=` в iplir; виртуальные
11.x/7.x/12.x выдаёт ViPNet), узел только с `virtualip` помечен «за NAT»,
несколько пар — несколько интерфейсов; узлы, которых в iplir нет, помечены
«нет в iplir», их число в шапке панели и фильтр-чип рядом с поиском. Строка правила ViPNet в списке — теги: имя правила (светло-оранжевый,
kind `name`) · источник (светло-голубой, side `src`) → назначение
(светло-серый, side `dst`) · сервис. Объект в стороне — кликабельное имя
группы (`group`); набор адресов/узлов — первые два и многоточие (`set`),
по клику карточка стороны `acl/<device>/<acl>/rule/<id>/<source|destination>/panel/`
(`acl_search.rule_nodes_panel`: узлы с парами адресов, литералы, объекты
ссылками, any); в панели объекта не-адресные члены (FQDN — объекты вроде
BBDNS_1 состоят из одних доменных имён) — строками `fqdn`, на старой
карточке объекта — таблица «Доменные имена в объекте» (`get_object_group`
отдаёт их ключом `fqdns`); лимит панели — 1000 строк; `any` — приглушённый тег; выключенное правило (`inactive`) — строка
приглушена и пометка «выкл.» у имени; сервис — светло-салатовый тег
(`service`), при более чем двух сервисах кликабельный, карточка через ту же
панель со стороной `service`. Ячейка правила — flex: имя и сервис не
сжимаются, ужимаются источник и назначение. Между блоками — иконки-разделители
(фрагмент kind `sep` с `icon` src|dst|svc, lucide-контуры через CSS-mask в
`acl.css`): перед источником крупная точка, перед назначением простая
стрелка, перед сервисом вилка; текстовых «·» и «→» в строке ViPNet нет, стикеры
без иконок. Доменные имена, `@local`,
`@tunneledip` и интерфейсы в карточке стороны — без подписей (это штатные
операнды ViPNet). Cisco и коммутаторы — синтаксис
устройства, стороны теми же тегами (`lit` — некликабельный литерал).
Узлы в результатах поиска (блоки «Откуда»/«Куда») — именами из iplir,
перечень узлов сворачивается в чип «Имя правила +N узлов»
(`_collapse_nodes`), идентификатор и адреса — в подсказке. Состав узлов режется по
«;» только вне скобок (`_split_members`): внутри скобок «;» разделяет пары
адресов одного узла.

Тесты: `ip_plan/tests/test_acl_search.py` — синтетическое устройство ViPNet с
вложенными объектами, исключением, смешанным операндом и широким набором.
На реальных снимках 10.1.141.166 даёт 17 правил на 2 устройствах — ровно
картина макета.

## Страница «ACL»: снимки политики доступа всех устройств

Страница без своих моделей: читает каталог `config_backups/<device>/`,
который ведёт `netbox_config_backup.py` из netbox-sync (bind-mount
`ACL_CONFIG_BACKUPS_DIR`, только чтение), и ничего не пишет ни в NetBox, ни
на диск. С 2026-10-01 это не только Cisco:

- `ip_plan/services/acl_model.py` — общая модель (`Endpoint`, `AclRule`,
  `Acl`, `Application`, `ParsedDevice`). Действие нормализовано в
  permit/deny/remark, слово вендора (pass/drop/reject) — в `action_raw`;
  имя правила, флаг «выключено», расписание и прочие вендорские колонки —
  в `label`, `inactive`, `schedule`, `extra`.
- `ip_plan/services/acl_parsers.py` — реестр «`parser` из `meta.json`
  (= `interfaces_parser` модели) → модуль → какие файлы снимка ему нужны»:
  `cisco_ios`, `eltex_status`, `eltex_mes24` (офисные MES24xx, тот же
  `eltex_acl`; ISS-синтаксис `ip access-list standard 10` + `permit any
  host X` он пока не разбирает), `maipu`, `huawei_vrp` разбирают `latest.cfg`,
  `xfw` (ViPNet xFW/HW) — `latest.firewall_rules.txt` +
  `latest.firewall_objects.txt` + `latest.iplir_config.txt` (по iplir
  разрешаются идентификаторы узлов `0x…` в VPN-объектах и туннельных
  правилах координатора: имя узла, его адреса и туннелируемые диапазоны;
  состав объекта «как есть» — `ParsedDevice.object_group_members`)
  (снимаются в KOI8-R — ключ `encoding`
  модели, иначе кириллические имена правил бьются, а колонки съезжают).
  Каталог без `meta.json` считается снимком
  Cisco (так выглядели бэкапы ASR до появления файла). Сломанный или
  отсутствующий парсер даёт пустое устройство с текстом в `warnings`, а не
  500 на всей странице.
- `ip_plan/services/acl_store.py` — кэш разбора по mtime всех файлов
  снимка, поиск по IP (попадание в исключение объекта ViPNet снимает
  совпадение; выключенные правила сортируются ниже), сводка `snapshot_info`
  (когда снято, когда менялось, версия политики — `rules_set_id` ViPNet),
  история `list_history` и `diff_snapshot` — unified diff соседних снимков
  одного имени, строки с секретами (`community`, `password`, `secret`,
  `key`…) маскируются до сравнения.
- Объекты в операнде хранятся списком `Endpoint.object_groups` (у ViPNet
  в одном Source бывают «@Admins nets, 10.1.141.166, …», kind `mixed`) —
  «используется в» и ссылки в ячейках считаются по нему, не по
  `object_group`. Имена объектов xFW различаются ведущим пробелом
  (« mdc-asutk-test» и «mdc-asutk-test» — два разных объекта с одной
  сетью), поэтому резолвер ищет сначала точное имя и только потом без
  учёта пробелов. Вложенность объектов — `ParsedDevice.object_group_includes`,
  в таблице объектов показывается как «входит в».
- У ViPNet списками становятся категории Local, Forward, Tunnel, Vpn и NAT
  (`vipnet_firewall.DEFAULT_SECTIONS`); Service-секции Generated в списки
  не идут. Формат xFW и координатора HW различается (Rule ID / только имя,
  `->` / `>`, Tunnel Rules, VPN-объекты без адресов, кириллица объектов в
  колонках как UTF-8-байты поверх KOI8-R) — всё это в докстринге модуля. На карточке они показаны вкладками (`siblings` в `acl_detail`),
  имена объектов в Source/Destination — ссылки на карточку объекта
  (тег `acl_endpoint` в `templatetags/ip_plan_extras.py`).
- Страницы: `/acl/` (поиск, обзор списков, объекты, снимки),
  `/acl/<device>/<acl>/`, `/acl/<device>/object-group/<name>/`,
  `/acl/<device>/history/?file=<снимок>` (diff).

SNMP community в колонке «Применён» больше не показывается — только
`community (RO)`; при добавлении новых «применений» не класть секреты в
`Application.location`, он рендерится как есть.

Тесты парсеров не требуют Django и гоняются на хосте:
`python3 -m unittest discover -s ip_plan/tests -t . -p "test_*.py"`
(`test_acl_store.py` без Django помечается skipped); `test_acl_store.py`
использует `settings` — запускать в контейнере:
`docker compose exec web python manage.py test ip_plan.tests.test_acl_store`.
Фикстуры в `ip_plan/tests/fixtures/` — синтетические, повторяют формат
живых выводов с вымышленными адресами; реальные снимки в репозиторий не
кладём.

Дизайн: `docs/plans/2026-10-01-access-policy-snapshots-design.md`.

## Настройки: площадка у устройства и у источника гипервизоров

Поле «Площадка» в форме устройства и в форме источника (RedVirt/vCenter) —
`<select>` из `dcim/sites` NetBox (`NetBoxClient.list_sites()`, обёртка
`sc.site_options()`), значение — slug (`mdc`, `rdc`, `office`). Площадки
заводятся в NetBox руками, синк их не создаёт, поэтому `sc.validate_site`
отклоняет slug, которого в NetBox нет, и пустое значение. Если NetBox
недоступен, список пуст: форма показывает текстовое поле и принимает любой
непустой slug — править конфиг при лежащем NetBox всё равно нужно.

В форме устройства блок «Размещение» стоит сразу под «Устройство», выше
реквизитов доступа: где стоит устройство — ключевой факт для общей карты
инфраструктуры. В списках устройств и источников площадка — чип
`.set-chip-site` рядом с именем (имя площадки из NetBox, slug в подсказке),
а не отдельная колонка: см. «Ширина таблиц» ниже.

`source_save` собирает объект источника заново из пяти полей
(`name/url/user/password/site`): ключ, дописанный в JSON руками, при
сохранении из формы пропадёт. У устройства наоборот — `device_save` стартует
с копии прежнего блока и незнакомые ключи сохраняет.

## Настройки: флаги сбора у устройств и моделей

Раздел «Настройки» правит `conf/devices.json` соседнего репозитория, где у
каждого флага два уровня — модель (`device_types`) и устройство. Синк читает
их слиянием «устройство поверх модели», и та же функция теперь одна на весь
`ip_plan` — `sc.effective(device_cfg, device_types)` в
`ip_plan/services/sync_config.py`; список самих флагов — `sc.SYNC_FLAGS`.

Что из этого следует для интерфейса:

- **Галочки в карточке устройства показывают эффективное состояние** (модель
  + устройство), как и чипы в списке. Пометка «включено на модели» стоит у
  тех, что устройству достались по наследству.
- **Снятая галочка сохраняется как явный `false`**, если шаг включён у
  модели (`device_save`). Просто удалить ключ нельзя: «ключа нет» означает
  «наследовать», и до 29.09.2026 интерфейс делал именно это — снять
  «MAC-таблицу» было физически невозможно, `sync_macs` задан у шести моделей
  из семи. В списке такие устройства подписаны «выключено здесь: …».
- **Флаги модели — умолчания её устройств и массовый выключатель.** При
  выборе модели в карточке устройства блок «Что синхронизировать»
  перерисовывается по её умолчаниям (htmx, `device_flags` →
  `_settings_device_flags.html`), а изменение флага в самой модели
  применяется ко всем её устройствам: их персональное значение убирается, и
  они начинают наследовать новое. Без этого «выключил у модели» не меняло бы
  ничего там, где флаг проставлен устройству лично, — а таких большинство.
  Устройство при этом вправе и включить шаг, которого у модели нет: так
  сейчас заданы интерфейсы, LLDP и VLAN.
- **Происхождение шага показано цветом чипа, а не подписью под строкой.**
  Серый с рамкой — задан и у модели, и на устройстве; голубой — унаследован
  от модели; жёлтый — включён на устройстве вопреки выключенному у модели;
  перечёркнутый — выключен здесь (с 02.10, см. «Настройки v2»). Классы
  чипов шагов не должны задевать чипы вкладки «Пользователи».
- **SNMP community нод кластера** (`snmp_communities`) — поле карточки
  устройства, хранится списком. Только для кластеров ViPNet: community там
  адресует ноду, по первой отвечает активная, по второй — пассивная. Синк по
  ним снимает состояние кластера и пишет в NetBox роль, время последнего
  переключения и достижимость соседа (см. `netbox-sync/CLAUDE.md`). Пусто —
  шаг не выполняется.
- **Валидации считают эффективную картину, а не блок устройства.** Заодно не
  дают сохранить заведомо неработающее: MAC без интерфейсов (синк снимает
  MAC хвостом шага интерфейсов) и `sync_macs` у `xfw` без
  `cluster=vipnet_failover`.

> [!warning] Форма модели правит **свои** поля, не пересобирая конфиг с нуля.
> Раньше `device_type_save` собирал словарь заново, и сохранение модели
> молча стирало всё, чего в форме нет: `cluster: vipnet_failover` у
> `xFW 5000` и `HW5000` — то есть один заход в карточку модели выключал
> сбор всего кластера криптошлюзов. Добавляя ключ, который синк читает,
> заводите ему поле (`_TYPE_TEXT_FIELDS` / `_TYPE_FLAG_FIELDS` /
> `_TYPE_LIST_FIELDS`) — иначе его хотя бы сохранит `dict(previous)`, но
> отредактировать будет негде.

Названия моделей проходят валидацию с `allow_spaces=True`: в NetBox это
`device_type.model`, где пробел законен и уже используется («xFW 5000»).
Без этого послабления такую модель нельзя было сохранить вообще — форма
отдавала её собственное имя, а валидатор его же и отвергал.

## Настройки: ядро сети, ARP и серийные номера (02.10.2026)

В карточке устройства — галочка «Ядро сети» (`network_core`): маршрутизирует
только xFW, префиксы площадки импортируются только с ядра. Сохранение не
пропустит включённые «Префиксы сетей» без «Ядра сети» (адреса на
L3-коммутаторах служебные). У модели — поля «Команда ARP-таблицы»
(`arp_command`, L3-коммутатор: IP ↔ MAC для построения связей) и «Команда
серийного номера» (`serial_command`, когда по SNMP номера нет). Как ими
пользуется синк — netbox-sync CLAUDE.md, раздел «Ядро сети, серийные
номера, ARP L3-коммутаторов».

## PostgreSQL и перенос с SQLite (03.10.2026)

С 03.10.2026 в `docker-compose.yml` есть сервис `postgres` (образ
`postgres:18`) с двумя базами: `ip_plan` (Django) и `netobs` (наблюдения
MAC/IP, схемой владеет netbox-sync). Решения и причины — в плане
`docs/plans/2026-10-03-0059-feat-observations-store-stage1-plan.md`
(KTD1–KTD4, KTD11). Отдельный контейнер, а не PostgreSQL боевого NetBox:
боевую СУБД не трогаем, локально и на проде всё одинаково.

**Роли и базы** (создаёт `db/bootstrap.sh`):

| Роль | Права |
|------|-------|
| `ip_plan` | владелец базы `ip_plan`; `CREATEDB` — ради тестовой базы `manage.py test`, больше ничего |
| `netbox_sync` | владелец базы `netobs`; под ней netbox-sync пишет наблюдения и применяет миграции схемы |
| `ip_plan_ro` | в `netobs` только `CONNECT`, `USAGE`, `SELECT` + `ALTER DEFAULT PRIVILEGES FOR ROLE netbox_sync` (новые таблицы остаются читаемыми); `default_transaction_read_only = on` — вторая защита |

Порт на хосте — `127.0.0.1:${POSTGRES_HOST_PORT:-5433}`, только loopback:
netbox-sync на том же хосте ходит в `netobs` на `127.0.0.1:5433`, снаружи порт
не виден. 5433, а не 5432 — на проде 5432, вероятно, занят системным
PostgreSQL боевого NetBox. Изнутри compose (`web`) адрес `postgres:5432`,
публикация для этого не нужна.

> [!warning] Том `pg_data` монтируется на `/var/lib/postgresql`, а не на
> `/var/lib/postgresql/data`. Образ `postgres:18` хранит данные в
> `/var/lib/postgresql/18/docker` и отвергает привычное монтирование на
> `.../data` (сделано ради `pg_upgrade --link` между версиями). Старый путь
> молча положил бы данные в анонимный том, и они пропали бы при пересоздании
> контейнера. **Никогда не выполняйте `docker compose down -v`** — флаг
> удаляет `pg_data` с обеими базами.

**Секреты разделены на два файла.** `.env` целиком уходит в контейнер `web`:
там только параметры подключения самого приложения (`IP_PLAN_DB_*`,
`NETOBS_RO_*`). `.env.db` читает только контейнер `postgres` (`env_file`):
`POSTGRES_PASSWORD`, `IP_PLAN_DB_PASSWORD`, `NETBOX_SYNC_DB_PASSWORD`,
`NETOBS_RO_PASSWORD`. У веб-приложения нет ни пароля суперпользователя, ни
пароля владельца `netobs` — компрометация `web` не даёт записи в наблюдения.
`.env.db` стоит в `.gitignore` **и в `.dockerignore`**: `Dockerfile` делает
`COPY . .`, и без второй строки пароли попали бы в слой образа `web`. На проде
оба файла пишет `.gitlab-ci.yml` из CI/CD-переменных (`.env.db` — с umask 077).
Пароль `netbox_sync` живёт ещё в одном месте — `netbox-sync/conf/netobs.json`;
при смене менять и там.

**`db/bootstrap.sh`** — идемпотентный скрипт ролей, баз и прав. На пустом томе
его выполняет образ (`db/initdb/10-ip-plan-bootstrap.sh`), на **уже
существующем томе init-скрипты образа не запускаются** — нужные роли, права
или смену пароля применяют вручную:

```bash
docker compose exec postgres bash /opt/ip_plan_db/bootstrap.sh
```

Повторный запуск ничего не пересоздаёт; переписываются только пароли ролей
(из `.env.db` — это источник истины). Смена пароля = правка `.env.db` (и `.env`,
где он продублирован) + запуск скрипта + перезапуск `web`.
`POSTGRES_PASSWORD` читается только при инициализации пустого тома, потом его
меняют `ALTER ROLE` вручную. Healthcheck делает `pg_isready` по TCP
(`-h 127.0.0.1`), а не через сокет: во время init образ поднимает временный
сервер только на сокете, и проверка по сокету объявила бы контейнер готовым до
конца `bootstrap.sh`. `entrypoint.sh` дополнительно ждёт базу сам: после
перезапуска хоста демон Docker поднимает контейнеры с `restart: unless-stopped`
без учёта `depends_on`, и `migrate` иначе падал бы в цикле рестартов.

**Перенос данных — `scripts/sqlite_to_postgres.sh`** (логика шагов — в
`ip_plan/services/db_transfer.py`, management-команды `db_transfer` и
`db_counts`). Запускается из корня репозитория при собранном образе `web` и
запущенном `postgres`:

```bash
scripts/sqlite_to_postgres.sh --stop-web          # рабочий перенос SQLite → база ip_plan
scripts/sqlite_to_postgres.sh --sqlite /app/data/db.copy.sqlite3 --pg-db ip_plan_xfer_test   # пробный
scripts/sqlite_to_postgres.sh --reverse --stop-web                                            # PostgreSQL → новый SQLite
```

Шаги: (1) копия SQLite через backup API и предпроверки источника (миграции на
версии кода, нет строк длиннее `max_length`, NUL и значений не того типа, нет
висячих ссылок, пароль LDAP расшифровывается текущим `SECRET_KEY`), затем
предпроверка цели (пуста, кроме засеянного миграциями); (2) выгрузка
`dumpdata --natural-foreign --natural-primary` без `contenttypes`,
`auth.permission`, `sessions`; (3) `migrate` на цели с `SEED_LOCAL_ADMIN=false`;
(4–5) удаление засеянных строк (`0003`, `0008`), `loaddata` и сброс
последовательностей — одной транзакцией; (6) `db_counts` цели = `db_counts`
источника по каждой модели, пароль LDAP читается, у `LocalAccount`/`MapLayout`
есть пользователь. Любая ошибка останавливает скрипт, рабочий файл
`data/db.sqlite3` не изменяется никогда (при прямом переносе читается копия, при
обратном пишется новый файл). Сессии не переносятся — пользователи входят заново.

- `--stop-web` останавливает `web` перед снятием копии; для рабочего переноса
  обязателен, иначе записи после копии в цель не попадут. Обратно скрипт `web`
  не запускает.
- **Переключатель скрипт не трогает**: в конце он печатает следующий шаг —
  `IP_PLAN_DB_ENGINE=postgres` (локально — в `.env`, на проде — CI-переменная и
  повторный деплой, потому что CI перезаписывает `.env` при каждом деплое) и
  `docker compose up -d web`. По умолчанию (`IP_PLAN_DB_ENGINE` пуст) — SQLite.
  Переключать на `postgres` без переноса нельзя: на пустой базе `migrate` создаст
  схему, а `ensure_local_admin` — `admin`/`admin`, и приложение поднимется как
  новое. На проде вместе с переключением ставят `SEED_LOCAL_ADMIN=false`.
- **Выгрузка лежит в томе `sqlite_data`**, каталог
  `/app/data/xfer/<время>-sqlite-to-pg/` (0700; внутри `source.sqlite3`,
  `dump.json`, `counts_source.tsv`, `counts_target.tsv`). Её **не удалять** —
  по ней проверяют границу отката. В выгрузке хеши паролей и зашифрованный
  пароль LDAP; на хост: `docker compose cp web:<каталог> ./`.
- **`db_counts`** — число строк по каждой переносимой модели
  (`--json`, `--output FILE`, `--compare FILE` — сверка с ранее сохранённым
  выводом, расхождение — ошибка).

> [!warning] Откат на SQLite возможен только до первой записи в PostgreSQL.
> Любая запись в любую модель после переключения (правка реестра, имена
> объектов `FirewallObjectName`, настройки) в SQLite не вернётся, а часть из
> этого отражает состояние реального xFW: имя объекта, ушедшее в команды,
> следующая генерация выдала бы заново. Перед откатом сравните
> `db_counts --compare .../counts_target.tsv` на PostgreSQL (ловит добавленные и
> удалённые строки, но не правки существующих) и, при сомнении, свежую выгрузку
> `db_transfer dump --output …` с `dump.json` из каталога переноса (входы
> пользователей меняют `last_login`, это ожидаемое отличие). Любое
> другое отличие — откат только обратным переносом (`--reverse --stop-web`):
> он пишет **новый** файл SQLite, и дальше его ставят на место
> `data/db.sqlite3` по инструкции, которую скрипт печатает в конце. Просто
> сменить `IP_PLAN_DB_ENGINE=sqlite` можно лишь тогда, когда в PostgreSQL
> ничего не писали.

**Бэкапы** — `scripts/pg_backup.sh`: `pg_dump -Fc` по каждой базе (`ip_plan`,
`netobs`) и `pg_dumpall --globals-only` в каталог на хосте вне тома
(`BACKUP_DIR`, по умолчанию `/var/backups/ip_plan_pg`), хранение
`RETENTION_DAYS` (14). Cron и проверка восстановления — в `DEPLOY_CHECKLIST.md`,
раздел 9.

Тесты ip_plan на PostgreSQL: `ip_plan` имеет `CREATEDB`, поэтому
`manage.py test` создаёт тестовую базу сам. Тесты выбора движка и переноса
(`test_db_settings.py`, `test_sqlite_to_postgres.py`, `test_db_counts.py`,
`test_compose_postgres.py`) проверяют настройки и логику без боевой базы.

## Поиск MAC/IP (03.10.2026)

Пункт бокового меню «Поиск MAC/IP» — `/obs/?q=…` (`views_obs.obs_search`,
`ip_plan/services/netobs_search.py`, шаблон `obs_search.html`, стили `obs.css`).
Отвечает на вопрос «где в сети виден этот MAC или IP» по истории наблюдений
netbox-sync (MAC-таблицы коммутаторов и ARP), а не по снимку, переписываемому
каждую ночь.

- **Доступ** — любой вошедший пользователь. Ищет по всем площадкам сразу,
  cookie площадки не читает: адрес ищут по всей сети.
- **Источник данных** — база `netobs` (схема в `netbox-sync/netobs/migrations`,
  моделей Django нет), сырой SQL через алиас `DATABASES["netobs"]`. Алиас
  объявляется **только** при заданных `NETOBS_RO_NAME` и `NETOBS_RO_USER`; роль
  `ip_plan_ro`, `connect_timeout` 3 с, `statement_timeout` 5 с — недоступная
  или подвисшая `netobs` не должна держать воркер gunicorn.
  `ip_plan/db_routers.NetobsRouter`: миграции только в `default`,
  `db_for_write` всегда `default` (явно, а не `None`: иначе объект, прочитанный
  через `.using("netobs")`, попытался бы сохраниться обратно туда).
- **Ввод**: MAC в любой из четырёх записей (`aa:bb:…`, `aabb.ccdd.eeff`,
  `AA-BB-…`, 12 hex); часть MAC от 4 hex — подстрока (`LIKE` с экранированием
  спецсимволов); IP — только точное совпадение; иначе понятная ошибка. По IP
  выдаются ARP-строки (`arp-table`, `arp-l3`) с этим IP плюс строки MAC-таблиц
  найденных в них MAC; чужие IP того же MAC (маршрутизатор в ARP ядра — десятки
  адресов) в выдачу не попадают.
- **Выдача** — не больше 200 строк, подпись «показано N из M». Колонки: MAC, IP,
  устройство, порт (+VLAN), источник, «адресов за портом», состояние, «впервые»,
  «последний раз». «Текущее» — строка есть в представлении
  `current_observations` (то же определение, что у топологии), иначе «прежнее».
  Пустой `first_seen` показывается как «до переноса» — запись импортирована из
  NetBox, когда адрес увидели впервые, неизвестно. Порядок: текущие первыми,
  затем порты с меньшим числом адресов (порт доступа, а не транк), затем
  свежие; прежние и импортированные приглушены.
- **Состояния страницы**: «не настроено» (нет `NETOBS_RO_*`) и «недоступно» —
  страница отвечает 200 с сообщением, остальное приложение работает как
  раньше; «опросы ещё не выполнялись»; «для этого IP нет ARP-записей»;
  «не встречался… последний успешный опрос — …».
- **Тесты** (`test_obs_search.py`, `test_db_routers.py`) мокают хранилище,
  тестовая база `netobs` не создаётся: схема принадлежит другому репозиторию.

## Ширина таблиц в разделе «Настройки»

С 02.10.2026 таблицы раздела — `st-*` в `static/ip_plan/css/settings.css`
(grid-строки, обёртка с рамкой и `overflow-x: auto`, колонки — `.st-cols-*`);
при 1280px на контент остаётся ~906px. Урок прежней вёрстки остаётся в
силе: раньше у `.set-panel` стоял `overflow: hidden` ради скруглённых углов. Таблица, которая
перестала влезать по ширине, при таком сочетании **молча теряет последнюю
колонку** — именно так пропали кнопки «Изменить»/«Убрать» после добавления
колонки «Проверка». Поэтому у `.set-panel-body-flush` включён `overflow-x:
auto` (переполнение прокручивается, а не срезается), а колонки держатся
узкими: статус проверки показан знаком (✓ / ✕ / – / …), а не словом, логин и
пользователь ушли подстрокой в ячейку адреса. Добавляя колонку, проверяйте
суммарную ширину — в браузере это `table.scrollWidth` против
`panel.clientWidth`.
